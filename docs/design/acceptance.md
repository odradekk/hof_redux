# 完整覆盖验收与 100 人负载基准

状态：已确认。Q1–Q10 逐项决定及 Q11 完整契约均经用户确认。对应[确定完整覆盖验收与 100 人负载基准](https://github.com/odradekk/hof_redux/issues/18)。这是验收规划基线，不表示已经执行实现测试、负载测试或真机验收。

## 本轮已确认决定

| 决定 | 验收约束 |
| --- | --- |
| Q1 起始硬件 | 单台 Linux，4 vCPU、8 GiB 内存、本机 SSD；应用、SQLite、Caddy 与备份按生产方案共同运行，压力发生器使用另一台机器。记录实际 CPU、磁盘、网络和软件版本。资源规格是实测起点，不是承载能力结论；不达标须定位瓶颈，调整实现或资源后重测，不直接降低已确认目标 |
| Q2 浏览器范围 | Android Chrome、iPhone Safari，以及 Windows Chrome、Edge、Firefox；每轮记录并固定验收开始时的最新稳定版本。至少一台真实 Android 和一台真实 iPhone 验证触控、软键盘与主要流程；桌面可结合自动化。旧版浏览器及微信/QQ 内置浏览器首期不承诺兼容，提示使用受支持浏览器 |
| Q3 常态操作组合 | 同时 100 人：40 人各每分钟一次普通冒险；20 人各每 15 秒一次模拟战；20 人各每 15 秒一次养成或交易；20 人各每 10 秒浏览一次战报或资料。额外叠加页面自动查询及真实备份、拍卖结算、统计与清理。错峰并遵守玩法资格，到点无法执行的操作照实记录；另测 Boss、竞技和集中竞价峰值。这些节奏不成为游戏冷却 |
| Q4 响应目标 | 普通查询和短写请求通过 HTTPS 入口测量，p95 ≤500 ms、p99 ≤1 s，并记录网络条件；已受理战斗从受理提交到结算提交 p95 ≤3 s、p99 ≤10 s。各操作分类统计，不能合并掩盖缓慢写入。手机体验、认证、重型管理查询与故障恢复另列 |
| Q5 错误及未执行比例 | 正常负载不允许重复扣发、部分结算、越权、丢失已受理结果或非预期系统失败。本来满足玩法资格的常态操作中，因全服容量、限流或压力脚本跟不上而未按计划执行的比例合计 ≤1%，逐类报告；预设的同 Boss/竞技串行竞争、版本冲突等另列，不能计作已完成业务 |
| Q6 时长 | 预热 10 分钟、100 人常态持续 1 小时，再做一次连续 8 小时稳定性测试。长测保持人数与操作节奏，按需切换预置合格账号，不修改正式玩法；检查内存、WAL、积压、备份和清理。峰值与故障另测，重大性能/运行修复后重跑相关测试 |
| Q7 历史数据 | 默认注册容量 500 个已创建账号；按 Q3 每天活跃 8 小时、累计运行 1 年生成等价历史，再按现有期限保留详情、凭据和最小防重记录。仅普通冒险约 1,728,000 份近 90 天正式战报、模拟约 1,152,000 份近 30 天战报；记录具真实结构和长短差异，不用空行代替 |
| Q8 峰值 | 每场独立预置合法状态，由同一批 100 个账号在 1 秒内分别对同 Boss、竞技场、同拍品提交，替代该批账号当时常态操作。允许玩法规定的忙碌/价格冲突，但不允许钱物或结果错误；请求 p99 ≤2 s，峰值结束后 30 s 内恢复常态响应。另测不同 Boss 及 100 笔拍卖集中到期 |
| Q9 手机体验 | 真机受控网络：下行 10 Mbps、上行 2 Mbps、RTT 100 ms。主要内容可操作的首次冷加载 p95 ≤3 s，站内切页及战报跳步 p95 ≤1 s；点击后 200 ms 内提供反馈，不提前宣布业务成功，骨架屏不算完成。另测断网、慢网、恢复前台及草稿/原结果核对 |
| Q10 认证与管理 | 正常认证请求 p95 ≤2 s、p99 ≤5 s；全服资产统计等重型管理查询 p95 ≤3 s、p99 ≤10 s。包含 100 账号在 1 分钟内登录和各类密码操作，叠加时普通请求仍达标；批量清理分别检验受理、进度及最终完成，不要求同步清完整批且不能无限积压 |

硬件、设备及版本必须出现在最终报告中，不能仅写“4 核服务器”或“手机测试通过”。此决定不购买服务器、设备或服务，不将某台开发电脑等同于生产验收环境。

## 沿用的覆盖和正确性门槛

- [保真基准](../legacy/fidelity-decisions.md)已经确定 45 个玩家能力条目、运营/公共能力清单，以及 15 职业、193 物品、268 唯一技能、147 怪物、24 地图、90 制作输出的内容基线。逐项记录新版实现、批准替代或明确不迁移的去向；数量相同不等于 ID、规则和可达性一致。
- [旧版证据入口](../legacy/README.md)及机器清单用于追溯来源；各专题后来批准的修复和行为差异决定新版预期。未开放定义保留且不开放，废弃实现不逐个重做；新版恢复码等已批准能力也必须验收，不能只检查旧清单。
- 每条公式验证运算顺序和整数结果；随机验证分布、区间、抽样次数及固定输入下的可复现结果，不复刻 PHP 随机序列。以公式对照为主，旧 Docker 代表性黄金样例抽检为辅；旧环境 PHP 版本在建立对照环境时核实。
- [状态与事务契约](state-transactions.md)要求原子提交、无重复扣发、流水一致和已受理操作恢复；[接口契约](interface-contract.md)要求正确区分持久终态、未知结果及单次请求拒绝，并覆盖迟到受理与手动封闭竞争。
- [手机契约](mobile-interaction.md)的 320/390/430 CSS 像素及桌面布局、至少 44×44 CSS 像素的主要触控目标、文字缩放、键盘焦点与字段标签等要求继续适用。正式玩家与管理流程均有验证归属，不能用原型、截图或代码审查替代真机操作。

### 规则证据与测试层次

纯规则测试验证公式、机制分支、边界与固定随机输入；使用生产数据库驱动和事务路径验证持久化、并发与故障；通过实际 HTTP 验证协议、权限和幂等；浏览器自动化与真人真机验证可见流程。不同层次各自承担可观察契约，不要求每条公式都从浏览器重复测，也不能用内存仓库替代 SQLite 提交/恢复证据。

黄金样例按战斗契约已有机制族和玩法模式选择，包括普通/模拟、Boss 及竞技；覆盖行动调度、条件与目标、伤害/治疗、持续状态、蓄力/咏唱、死亡/复活/召唤及战中成长等重要交互。每个正式机制族须能定位代表性验证，不将“抽了若干战斗”作为充分覆盖证明。对批准差异分别记录旧观察与新版预期；不得为了通过对比而回退已批准修复。对照环境仅使用必要旧代码、素材和合成测试数据，隔离网络及生产凭据。

随机验证以准确映射和边界为主：有限整数抽选验证各区间大小、端点、无掉落区间和独立抽样次数；稀有结果通过受控随机输入覆盖，不能因一批样本未出现就当作没有该结果。固定种子重放验证可复现性及事件顺序。需要统计抽样的部分在实施前登记样本量、种子及统计判据，依据目标概率和可发现的偏差确定；不靠反复换种子“刷到通过”，统计抽样也不能替代可精确验证的算法与区间检查。

并发正确性测试用可控制的提交/演算边界制造竞争，不靠碰巧同时点击或任意等待。分别检查双方都可能先提交的顺序、响应丢失、重启、旧执行者迟到、成功与取消/封闭互斥。记录业务前后快照与流水，核对每件装备的唯一归属以及金钱的合法收入/消耗/托管转移；掉落或打工等合法创造资产不能误按总量恒定断言。

扩展能力使用隔离的测试内容包验证已有机制的组合、装载、引用校验、展示和既有业务使用，不把这些测试内容发布成新增玩法。使用旧版精炼、附加效果及技能机制检验模块职责；新增机制仍需具名代码和参数校验，不承诺所有未来系统仅靠 JSON 完成，也不为验收实现任务、家园或通用插件平台。

### 测试数据与环境

空服初始化、常态历史库、临界状态和故障数据分别准备；禁止使用旧玩家存档、凭据或生产备份冒充测试数据。历史库用新版有效结构及引用关系生成，保留不同队伍、装备、事件长度、文本、状态和时间分布，不能大量复制同一压缩友好载荷来夸大备份效率。完整输入/复现材料、流水、终态、过期回执及历史版本均按各自期限和引用约束准备。

500 账号历史库覆盖默认满容量；正常注册性能场景另准备尚有容量的隔离数据，满容量拒绝另测。长时测试提前准备角色、技能、装备、材料、合法资产和账号切换计划；运行中不直接补余额或关闭资格校验。需要更换账号时仍只有 100 个计划中的活跃玩家，不能通过并发账号无限增长完成原定负载。

生成器参数、合成种子、行数和实际字节数纳入报告；完整战报、内部材料、索引、WAL、备份临时副本及远端仓库分别量测。没有生成足够历史数据、用空表代替、关闭日志/同步或遗漏后台任务的结果不能宣称本基准通过。磁盘容量和 I/O、备份上下载带宽由实际占用及恢复演练确定并锁定；超过已验证数据范围或显著调整留存/容量时重新评估，不能把首年基准当作无限增长承诺。

### 负载计时和统计

常态 Q3 是计划中的业务意图，不是每秒 HTTP 数，也不是每个页面只发一个请求。脚本按正式客户端协议发出必要请求及自动查询；在运行前固定操作子类比例、账号分配、轮询周期、内容/队伍/报告长度组合和后台任务安排。养成/交易组须实际执行不同操作，不能全部换成最快的一个端点。配置、种子和脚本版本随报告保存，失败后调整须明确记录并重新测量。

每个计划时点记录实际发送、受理/完成、明确拒绝、未发送和未知结果；因慢响应错过的时点不能从分母消失，不能用之后补发覆盖当时未执行。符合资格却因旧业务处理过慢持续占用而错过时点，也须报告其处理延误，不能把它当作原先就不满足资格而排除。压力发生器自身资源不足时报告无效环境或 Q5 未执行，不能称服务已经承受未实际发出的负载。

发送计划必须独立记录：仅等待上次完成才开始下一次的闭合负载会在服务变慢时自动降低到达量，不能单凭维持 100 个虚拟用户就证明既定节奏达标。这是测量方法约束，不指定必须使用某个压测工具。[Grafana k6 对开放与闭合负载的说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

Q5 的分母是符合预置玩法资格的常态业务计划数，自动轮询、结果查询和重试不能增大该分母稀释拒绝；系统错误不因数量低于 1% 而被允许。按操作类别报告成功样本数、未执行原因和分位数，保留时间序列以识别后半程恶化。结果未知、未完成或超时不能从报告删去；请求延迟与业务受理到结算耗时分开，查询间隔造成的显示延迟也单独记录。

报告写明分位数算法与样本数；样本不足的操作补做相同环境下的专项测量，不以单次执行声称尾部延迟达标。短请求完成不等于长业务成功；受理后的正常战败/平局是完成，演算错误后的故障取消是故障结果，不能当作快速完成样本使性能通过。战斗计算、等待工作线程及结算等待均计入受理到结算耗时。

常态与长时测试均使用 Q4/Q5，不只验收前几分钟。备份每 5 分钟实际生成和上传，拍卖真实到期，统计与分批清理按固定安排重叠；有到期数据和历史数据可处理。测试结束停止新操作后须核对在途任务和资产一致性，不能依靠重启清空内存掩盖积压或泄漏。

备份新鲜度以真实可用远端恢复点计量；正常测试若进入备份过旧、时钟或磁盘保护，必须记录原因并判定相关运行门槛未通过，不能把保护期间从正常样本中静默删去。首次全量备份与完整恢复另行计时；稳定运行前准备环境不等于已证明初次备份或恢复速度。

峰值场景单独准备资格、资金和物品，记录 100 次计划是否实际在 1 秒内发出、各响应及提交顺序。统计拒绝和成功的延迟，不以只剩最快成功请求的分位数判定；原有终态不被随后请求覆盖。不同 Boss 分别有受理机会，仍遵守全服名额；同一 Boss/竞技场若前场已完成，可以再受理，不能错误要求整秒内永远只成功一次。拍卖集中到期须核对每笔的截止与唯一结算，不能只测扫描函数运行时间。

峰值结束以最后一个计划突发请求实际发出为起点，不等所有慢请求结束后才开始计算恢复时间。继续常态操作并观察恢复后的样本、未完成业务及工作线程名额；分位数样本不足时重复独立峰值轮次并保留每轮时间线，不能以一次快速健康检查证明已恢复。串行忙碌可合法拒绝，但预置可受理且服务空闲的场景必须有实际受理/结算证据，不能“全部忙碌”通过验收。

### 真机、认证和管理验证

真机记录设备型号、系统、浏览器完整版本、视口、字体缩放及实际测得的网络条件。冷加载清除相关资源缓存，分别准备未登录入口和有合法会话的主要页面；从导航开始计到主要内容呈现且关键控件可用。站内切换和战报跳步从操作开始计到目标内容一致呈现；旧内容、骨架或按钮变色不能代替目标加载完成。点击反馈单独计到可见反馈，不能把业务真正完成的时刻提前。

重复测量可由真机自动化辅助，人工仍须实际核对触控、软键盘、安全区域、焦点、可读性、错误提示和流程理解；桌面设备模拟不能冒充 Android 或 iPhone。正式玩家和管理能力按手机契约全量登记，少数原型主流程通过不等于其他功能通过。跨设备编辑、刷新、断网、会话失效、发布更新和恢复代次变化按接口契约验证，草稿丢失边界不能改为未批准的长期保存。

认证请求时间包含密码计算及有界等待，不降低已确认密码哈希参数来通过性能验收；注册/恢复所需的后续界面与一次性恢复码另核对。100 账号登录由既有玩家依次重新建立会话，不能靠额外增加 100 个持续活跃玩家改变基准解释。故意超出认证限流的测试另行记录，不将正常登录误限流归为成功。

重型管理查询必须实际扫描或聚合约定数据并返回一致结果，不能用陈旧缓存或空统计替代。批量清理记录固定目标数量、逐批进展、总耗时、重试及中断恢复结果；在正常数据到期速率下，例行清理处理能力必须超过新到期数据产生速率，积压不能持续增长。最大测试批任务必须真正结束并核对全部固定目标，不能仅凭“已受理”或进度条宣布通过；具体批次、超时和告警参数按运行契约在实施中锁定。

### 实施交付证据

每轮报告保存应用提交、内容/规则/素材版本、镜像及依赖摘要、服务器与设备、数据库与历史数据量、脚本及测量口径、逐类结果、故障/恢复过程、缺陷和复验链接。可公开报告去除凭据、会话令牌、原始 IP 和私有完整输入；需要受限保存的诊断材料另行控制访问。

线程/名额、执行预算、超时、租期、清理批次、认证并发、限流、轮询、磁盘余量等实施参数必须有最终值与依据，且在报告对应版本上实际验证。未锁定或未验证不能以“以后配置”通过上线门槛；不能通过缩短已定留存、删除正式机制或增加未批准玩法限制来达到性能指标。

### 完成判定与人工验收

实现各阶段可提交阶段报告，但稳定版完成必须同时满足全部正式能力覆盖、批准规则与内容、正确性/权限、真机、负载、备份恢复和发布门槛。缺一类正式系统、存在错误结算或未完成恢复演练均不能称为整体完成。代码覆盖率、文档数量和自动检查数量不是替代指标。

每项结论仅使用“已执行通过”“已执行未通过”“未执行”或有批准依据的“不适用”；不适用必须指向具体范围决定，不能以开发困难或尚无设备为理由。复验关联原缺陷及修复版本；影响规则、数据、存储、并发、页面流程或运行参数的变更重跑相应测试，重大性能/运行修复按 Q6 重做相关负载及长时验证。

AI 提供可运行构建、覆盖清单、自动化与真机证据、性能及恢复报告；用户实际试用主要玩家流程和常用管理操作，核对体验并确认最终报告。用户不必手动重复每个公式或并发测试，但代理不能把自己的文字评审当作用户体验验收。

所有硬门槛未通过项都阻止稳定版完成。仅不影响正确性、安全、内容完整性、可读性、可操作性或既定性能的轻微外观问题，可逐项列明影响并经用户明确接受后延期；不得自动归类为“以后优化”而略过。验收通过不自动授权购买、生产部署或开放运营，这些仍按项目授权流程执行。
