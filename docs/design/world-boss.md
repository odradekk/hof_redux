## 已确认

- Q1：每个 Boss 同时只受理一场挑战。忙碌时其他新请求直接返回“正在战斗，请稍后再试”，不排队、不预留体力、不产生冷却；不同 Boss 的挑战可分别进行。同账号仍遵守一场未终结正式战斗的限制。
- Q2：20 分钟冷却由同账号的所有世界 Boss 挑战共用，从成功受理时起算；胜利、败北、行动上限平局都产生冷却。服务器故障最终取消的挑战不产生此次冷却。即使已过 20 分钟，未终结的原操作仍占用账号，不能另开正式战斗。
- Q3：每次受理按当时已创建且未删除的账号总数重新计算人数相关 HP 上限及经验/金钱基数，包含不活跃账号，不使用在线人数。已保存 HP/SP 原值延续，不因人数增减按比例调整；人数减少导致剩余 HP 高于新上限时也不主动截断。
- Q4：保留按当前时区/小时求值的原复活条件；一旦检查成立，就原子保存满 HP/SP 的新轮次。复活不会因时段结束而撤回，不再仅在查看页面的内存中复活。
- Q5：Boss 随机随从与地图一样严格按配置权重抽选，修正旧首项多一个结果的偏差；每名独立、有放回抽样，固定随从及追加数量不变。扩充 LEG-20 的适用范围。
- Q6：新服首次初始化时为 2000–2011 的 12 种模板各创建一个 Boss 实例，以初始化时人数计算满 HP/SP，立即出现；之后遵守各自复活条件。“早餐”等名称不额外限制首次出现时间，不迁移旧服运行状态。
- Q7：击败时间由成功结算确定。在结算事务内取得服务端时间，与本轮死亡、玩家收益及战报一起提交，失败不留下击败时间。复活等待不使用受理时刻或故障前未提交演算中的时间；账号冷却仍按 Q2 从受理时起算。

例如 12:00 受理、12:01 完成，12:20 可再次挑战任何 Boss。结算事务记录的下一次可挑战时间以原受理时间为基准，不使用完成时间；原操作恢复不重置起点。受理前拒绝不修改上次有效冷却。

路径缩写均相对 `old_hof/`。读取的是源码，不是旧 Boss 或玩家存档。

### 复活状态转换

Boss 模板、具体实例和轮次分开。实例保存当前轮次、存活/已击败状态、共享 HP/SP、最近击败时间、共享状态版本与当前挑战占用。轮次有稳定身份，复活新建轮次，不能复用旧轮次的击杀凭据或挑战结果。

已击败状态且无挑战占用时，按一个服务端时刻及有效部署时区计算 `cycle(now)`，条件仍为 `lastDefeatedAt + cycle(now) < now`。保留严格小于：恰好到点不成立，下一秒才成立。餐时是当前小时的周期分支，不是一天一次的固定刷新，不在死亡时固化一个永久不变的 `respawnAt`。

例如早餐 Boss 在 05:00 被击败，07:00:00 尚不满足严格比较；07:00:01 可复活。若当日 07 点内没有任何检查，到 08 点检查时使用 72 小时分支，不补发错过的窗口。Q4 保证如果已在 07 点完成复活，08 点不会因分支变化重新变为死亡。

地图/详情查询、挑战处理及运行任务可调用同一复活检查操作；实际状态转换在独立短事务中持久化，竞争者只允许一个创建新轮次。复活成功不依赖随后某位玩家能否通过体力、队伍等挑战检查，失败挑战不能撤回复活。查询只返回已经提交的存活状态；维护冻结新业务写入时同样暂停新的复活转换，继续显示已提交状态。任务频率归运行专题，不承诺窗口内必有检查。

当地小时采用已确认的部署时区；夏令时跳过某小时就没有该短周期分支，重复小时的两个实际时段均按该分支判断。时区或内容配置切换只影响此后的检查和受理，不撤销已发生的复活/击杀或改写已受理输入。实例已死亡时的周期按当前有效规则判断，切换不重置最近击败时间。

击败时间按 Q7 在成功结算中记录。Boss 本体死亡但随从仍存活时，按旧引擎继续战斗；本轮只在整场结算成功时完成持久的死亡转换。演算过程中不能提前开放复活或发放可领取奖励。

## 随从、共享状态与奖励

敌队默认是 4 名随机随从加 Boss；2003 为 6 名随机随从加 Boss，共 7 名，不能套用玩家的五人上限。2004–2006 先加入固定随从 1099，再追加 3 名随机随从，最后插入 Boss，共 5 名。`SlaveSpecify` 不是替代随机名单（`class.main.php:348–374,2821–2832`）。Boss 插入随从列表的 `floor(随从数 / 2)` 位置，保留初始顺序。

随从权重使用 Q5 的 1–总权重算法，抽样结果、外观、站位及掉落在受理前完成并固定；每次新挑战重新构建随从，不把上一场随从的血量、死亡或召唤物留给下一位玩家。Boss 的 HP/SP 跨战保存，其战斗临时状态、行动/条件计数、蓄力咏唱和临时属性按旧初始化重建。

Boss 候选掉落也在每次受理时抽取并固定，不在复活时给整轮只抽一次，也不等到击杀提交时重新抽。沿用固定 1–10000 区间及其无掉落区间。只读展示不创建新挑战的随机输入。旧挑战中两次 `CreateMonster` 调用的随机推进分别记录：实际 Boss 构建取自己的掉落，后续为 `UnionMob` 元数据重复构建产生的抽样仅推进随机状态，不覆盖实际掉落（`class.main.php:2788–2792`、`class.union.php:237,274`）。随从与战斗的随机起点同样分别记录，恢复不用错阶段的状态。

### 经验与钱物

按战斗契约保留两个经验来源：每次检查 Boss HP 差额的经验，以及新死亡时额外产生的整份 `DropExp`。差额为 `LastHP - HP`，先更新 LastHP，若差额为负则本次为零，否则为 `ceil(exphold × 差额 / 定义maxhp)`（`class.union.php:224–229`）。分母不是战斗中被临时改变的 MAXHP，不能改成整场累计净伤害或只在胜利后计算。

Boss 回血后会更新差额基准，再次扣除这段 HP 仍按旧规则产生经验，不加全轮经验封顶。经验先按候选检查所属的行动方及既定 `GetExp` 流程确定接收队伍；归玩家队伍的经验才由该时点存活玩家角色均分，死亡角色与召唤物不参与。各事件的倍率与取整按既定战斗契约，不以最终存活名单重新分配。

持续伤害不会自动作为玩家贡献入账。旧引擎在行动开始处理持续回复/毒伤，在技能后检查整个候选集合，再将检查所得经验交给行动者一方（`class.battle.php:460–463,619–682,801–815`）。例如 Boss 中毒后，若其技能候选不含自己，差额可延后到以后包含它的检查；若己方/自身技能使它被本方检查，差额基准被推进，玩家不会因此收到经验；如果战斗结束前没有对应检查，也不追加补发。保留这一时序，不另做“所有毒伤归玩家”的结算。

Boss 死亡钱物及击杀经验按引擎的实际收益事件归属本场；此前其他账号不获得事后贡献分成。随从及其他怪物的有效击杀收益照常累计，最终败北或平局不抹掉这些收益。不能看见 Boss HP=0 就另行补发尾刀包：自我牺牲等分支的收益接收行为仍按战斗契约，不能绕过引擎增加一份奖励。

每轮只允许一个成功的致死结算来源，关联轮次与挑战操作；它用于去重与核查，不新建贡献排行榜或全服分钱系统。即使本场先杀 Boss、后败给随从，也按真实事件结算，轮次仍进入已击败状态。

### 复活首战的差额经验初始化

旧复活分支先把内存 HP 恢复为满值，却将 LastHP 设为持久旧 HP=0（`class.union.php:283–290`）。如果第一次包含 Boss 的候选检查前它已经受伤，这一段差额会漏计；如果此前已有未伤到 Boss 的候选检查，则基准可能已被校准，并非首个命中必然漏经验（`class.battle.php:673–682,801–815`）。

按已批准的明确缺陷处理规则，新版每次挑战将 LastHP 初始化为本场实际起始 HP，包括复活后的首战；不把上一场的差额检查变量持久化。以满 HP=1000、经验基数=500 为例，首次有效检查前降到 900，应产生差额经验 50（未乘倍率、未按角色分配），不能因旧持久 HP=0 得到零。这是初始化修复，不改变两种经验来源及其计算顺序。

## 并发与操作协议

### 受理

一次短事务中识别同请求的已有操作，再检查账号资格、冷却、体力、角色与装备、Boss 的存活轮次及是否被占用。固定完整输入、敌队、内容/规则/随机版本与初始状态，建立账号/角色/装备和本 Boss 的占用，预留 10 体力，按选择保存记忆队伍后一起提交。

同请求重试先返回原操作，不被自己留下的 Boss 忙碌状态误拒绝；同请求身份不能更换参数。新请求遇到繁忙 Boss 不是已受理操作，不建立等待队列。客户端只有获得本次受理成功后才可显示本场已开始。

Boss 占用与轮次/共享状态版本持久保存。唯一受理条件在数据库事务内验证，不能依靠进程内布尔值；重启不能让另一场抢先使用仍被占用的 Boss。受理后的 Boss 状态由原操作负责完成或正式取消，管理员及任务也不能越过占用直接改血或复活。

### 演算与结算

战斗在事务外按完整快照演算。执行权到期只允许原操作被新执行代次恢复，不释放业务占用；旧执行者的迟到结果必须被拒绝。恢复不使用新装备、新敌队或重抽的掉落，不在新的 Boss 状态上悄悄重算同一场。

结算校验原操作、执行代次、Boss 身份/轮次/状态版本及占用归属，将共享 HP/SP、必要击败信息、角色成长、10 体力实际支出、钱物、账号冷却、流水、战报和操作终态原子提交，再释放全部占用。结果涉及的钱包增减应用于当前状态，不覆盖期间不相关的账号变化。

由于本轮 Boss 由该操作独占，正常挑战之间不需要合并伤害或竞争着领取同一次击杀。若结算时共享版本意外变化，不能以旧快照覆盖它，须查明非法修改/恢复冲突并按事务契约处理。任何一场旧轮次结果都不能修改复活后的轮次。

### 故障

受理后断线、进程停止或短暂数据库忙时保留原操作与占用，恢复同一输入。确实无法完成时，在确认尚无成功结果后原子取消、释放体力预留和占用，不产生本次收益或冷却；记忆队伍属于已保存配置，保留它。租期到期不等于可以退款或开放新挑战。

结算已成功但响应丢失时，重试返回同一结果；既不能再次发奖，也不能再走取消释放。取消与成功只允许一个终态获胜。玩家不能靠断网或看见不利结果来撤销挑战。[运营契约](operations.md) Q8 将常规工具限定为诊断、按规则检查复活、挑战恢复和故障取消；共享状态损坏另做明确的事故修复方案，不提供日常改血、强制击杀或提前复活按钮。

## 发布与验收边界

短维护发布先排空挑战，保留每个实例的轮次、HP/SP及击败时间。此后新受理使用新内容的属性、战术和奖励，不按旧定义版本永久冻结 Boss；不得自动复活、按比例补血或清除死亡进度。移除仍存在的 Boss 实例、变更其类型或产生其他不合法状态时须显式迁移，不能凭同编号覆盖或删除旧轮次；管理员修正也须通过所属操作与审计。

公开查询提供 Boss 名称、挑战资格/总等级限制、存活/忙碌/冷却等信息，并按[展示契约](public-information.md) Q15 公开当前已提交的精确剩余 HP/SP 和相应上限。上限按查询时账号数及当前定义计算并标明口径；人数减少导致剩余 HP 高于上限时照实显示，不改写状态。旧版战斗专门隐藏精确 HP/SP（`class.union.php:104–125`），现已作为批准展示差异处理。历史战报显示本场已保存的实际值及变化；尚在演算的临时状态、完整战术与复现输入不直接返回浏览器，查询不抽取未来挑战的随机输入。正式战报公开、正常保留 90 天及管理清理例外同见展示契约。

| 查询 Boss | 当前实例、有效时区与账号资格；必要时执行统一复活检查，返回已提交可见状态，不抽取下一场敌队 |
| 提交挑战 | 请求身份、Boss 实例、所选角色与配置版本、记忆选项；受理固定轮次及完整快照，返回操作状态或具体拒绝原因 |
| 查询/恢复挑战 | 账号权限与原操作身份；返回原记录，恢复原输入及版本，不创建新轮次或新抽样 |
| 检查复活 | 实例、同一当前时刻/时区/内容及人数上下文；只在未占用且符合条件时提交一次新轮次 |

| 验收场景 | 必须成立的结果 |
| --- | --- |
| 两账号同时挑战同一 Boss | 只有一场受理；另一场忙碌拒绝，无预留、冷却或记忆变更 |
| 两账号挑战不同 Boss | 不建立全服 Boss 队列，各自持久占用；共享数据库只用于短事务 |
| 同账号改打另一 Boss/普通战 | 未终结正式战斗仍阻止新正式受理，不能绕过角色及账号占用 |
| 20 分钟到点、晚结算、取消 | 以受理时刻加 20 分钟判断；原战斗未终结仍不能再战；取消不新增冷却 |
| 两次复活检查竞争、旧轮次结果迟到 | 只创建一轮；旧结果因轮次/占用/终态与执行代次校验不能写入新轮 |
| 新服初始化、重启及重复初始化 | 新服 12 种各一个满状态实例；已有实例的 HP/SP、轮次和击败时间不被重置 |
| 餐时窗口边界与查询后的跨时段 | 按当前小时动态判断，严格到点不成立；已持久复活不撤回 |
| 账号数增减及重启恢复 | 新受理重新采样，原操作恢复不变；已有绝对 HP/SP不主动缩放或截断 |
| 普通/土匪/餐时 Boss 编队 | 分别验证 5/7/5 个初始敌人；指定随从与随机随从并存，顺序不变 |
| Boss 已死但随从尚活 | 按引擎继续，最终结算保存死亡及有效收益，不提前再次开放 Boss |
| 回血后再扣血、伤害经验加击杀经验 | 保留事件级奖励，不能以全轮净贡献替代或按最终幸存者重分 |
| Boss 中毒后使用敌方技能/己方技能，或战斗结束前再无对应检查 | 按候选检查和行动方保留延后、Boss 方消费或不补发；不将持续伤害自动补计给玩家 |
| 复活首战首次候选检查已受伤/未受伤 | LastHP 从实际起始 HP 初始化，两种路径均无漏发或重复差额经验 |
| 断线、租期到期、重复提交及取消竞争 | 恢复同操作、原随机输入及版本；不重复扣费/发奖，终态唯一 |
| 致死演算后长时间故障，恢复成功结算 | 冷却保留原受理起点，复活等待从本次成功结算记录的击败时间开始；未提交致死不允许提前复活 |
| 维护更新与长期 Boss 状态 | 排空后新内容生效，轮次及已保存进度保留，不非法重置或移除实例 |

这些是待实施场景，不表示新引擎、数据库并发、旧运行对照或 100 人负载测试已通过。
