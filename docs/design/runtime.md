# 单机部署、定时任务与备份恢复方案

状态：已确认。Q1–Q30 及 Q31 完整契约均经用户确认。对应[确定单机部署、定时任务与备份恢复方案](https://github.com/odradekk/hof_redux/issues/17)。本文件是运行规划，不表示已部署或验证承载、备份和恢复能力。

前置：[SQLite 决定](../adr/0001-sqlite-for-initial-operation.md)、[状态与事务](state-transactions.md)、[战斗](combat-contract.md)、[冒险流程](adventure-flow.md)、[内容发布](content-release.md)、[账号](accounts.md)、[运营管理](operations.md)。相关业务还须遵守[交易](trading.md)、[竞技](arena.md)、[世界 Boss](world-boss.md)与[展示](public-information.md)契约。

## 已确认的目标

- Q1：首期生产部署采用单台 Linux 服务器与 Docker Compose，数据库和备份位于服务器持久目录，应用以容器发布；本地可继续使用 Windows 开发。本轮不购买服务器或部署生产。
- Q2：整机或磁盘损坏时，以最多损失最近 15 分钟进度、开始人工处理后 2 小时内恢复为首期目标。自动生成并传送异机备份，须通过实际恢复演练验证；同一服务器上的备份不能覆盖整机丢失。不承诺全天候值守，故障发生至人工开始处理的等待时间另算。普通进程崩溃恢复已受理操作，不通过回退数据库处理。
- Q3：异机备份采用独立于游戏服务器、支持 S3 接口的对象存储；上传前加密，恢复密钥在游戏服务器之外另存。数据库、对应应用/内容版本和恢复所需配置均须可找回。具体服务商及费用实施时选定，本轮不购买；运行数据库仍只在本机磁盘上。
- Q4：保留最近 24 小时的频繁恢复点，以及每天 1 份、保留 30 天的备份，到期自动清理。备份为整份历史快照，可能包含线上删号或记录清理前的数据，直至该备份到期；只用于受控灾难恢复，不作为后台历史查询入口，恢复后重新执行已确定的到期检查。
- Q5：最新可用异机备份覆盖的数据落后超过 15 分钟时自动进入保护性暂停并告警。暂停玩家与后台业务写入，保留只读访问及备份/诊断；已受理战斗保持待处理，不取消、不重新抽结果。新的异机备份完成并校验通过后才恢复；拍卖仍按现实时间截止。接受对象存储或备份持续故障会影响游戏可玩性的代价。
- Q6：从旧备份恢复时先隔离旧服务器和执行者，再开启新的恢复代次，所有玩家和管理员旧会话及旧页面操作请求失效。玩家须重新登录、刷新并核对恢复后状态，旧页面不能自动重试购买、竞价等操作；备份内已受理战斗由服务器按原记录恢复。管理员身份须由服务器管理者重新授权后启用。凭据和生命周期回退政策见 Q7。
- Q7：接受玩家密码、恢复码及账号停用/删除状态回到所选备份时点。备份后改密、恢复码消费/重签、停用和删号可能丢失，旧凭据可能重新有效；撤销旧会话不能阻止持有旧凭据者重新登录。恢复时公布实际恢复点和受影响窗口，提示玩家核对并改密；首期不另建异机安全变更日志。账号仍按稳定内部身份恢复，不按可复用名称合并不同身份。
- Q8：每日自动实际下载、解密并验证一份异机备份，检查数据库及对应版本。上线前、以后每月及备份/恢复流程修改后进行完整恢复演练；在隔离环境恢复到可登录、可继续处理已受理业务，从人工开始处理起计时，验证 2 小时目标。隔离环境不得接入生产写入或执行生产管理操作；接受额外磁盘、下载流量和每月人工验收成本。
- Q9：SQLite WAL 显式采用 `synchronous=FULL`，业务提交返回成功前完成必要磁盘同步，优先保障已提交业务的持久性；目标服务器须验证写入延迟与吞吐。耐久性依赖操作系统、文件系统及磁盘正确落实同步，不把该设置视为磁盘损坏或整机丢失的保障，后两者仍按异机备份恢复。[SQLite 持久化设置](https://www.sqlite.org/pragma.html#pragma_synchronous)

## 已确认的执行与调度

- Q10：一个后端应用进程负责请求、受理和结算，使用数量受控、重复利用的战斗工作线程池。工作线程只读取本场固定输入并返回演算结果，不访问数据库；线程数量按服务器配置和负载验证确定。首期不增加独立战斗服务或消息队列，仍为单机模块化单体。数据库调用所在的线程与连接安排见 Q18。
- Q11：拍卖每 5 秒扫描到期记录，正常运行时以到期后 10 秒内完成结算为首期验收目标。到期即禁止竞价，到账可以稍晚；逐笔短事务结算，一笔异常不拖住其他拍卖。重启或维护结束后立即扫描补结算，保护性暂停期间不写入；维护或故障期间不承诺 10 秒目标，不改变截止时间。
- Q12：世界 Boss 每 30 秒自动检查复活，查看或挑战时额外按当前时刻检查；按原复活条件在事务内确认，每轮只复活一次。维护或保护性暂停期间不复活，恢复后按当时的时区和时刻检查，不补算停服期间已错过的特殊时段。
- Q13：普通冒险、模拟战、Boss 和竞技挑战均在受理前检查可用处理名额；容量满时直接提示稍后重试，不预留体力、不产生冷却、不保存本次队伍或战术修改，不先受理再无限排队。已受理但因故障等待恢复的战斗保留原记录并优先恢复；Boss 和竞技场各自的忙碌限制仍适用。具体名额通过负载验证确定。
- Q14：确定性演算错误可自动故障取消。先用原版本、原输入和原随机状态在新工作线程中复核一次；仍出现同一确定性错误时，确认没有已提交结果并使旧执行者不能提交，再原子取消、释放预留和占用，记录原因并告警，不计胜负或收益。数据库暂时不可用、进程崩溃、演算超时或版本文件暂时找不到，不能仅因此自动取消，须保留原操作恢复或交管理员核查。
- Q15：进程和数据库恢复健康后，60 秒内开始恢复已受理操作。同一操作遇到临时执行或结算故障，分别等待 5、15、30 秒进行三次自动重试；三次重试仍失败，保留原操作与占用并告警，交管理员恢复或按既定条件取消。受理满 5 分钟仍未完成也告警。明确维护、备份保护性暂停或数据库整体不可用期间不空转重试、不耗尽次数；接受顽固故障需要人工介入，不能保证无人值守时自动解除占用。
- Q16：模拟战维持同账号同时一场与全服处理名额限制，不增加两场之间的独立冷却；上一场完成后即可再次测试。容量满时按 Q13 拒绝，重复请求只处理一次，接口仍受通用请求限流保护；不为正常模拟增加体力、每日次数或独立等待时间。

## 已确认的运行时与存储调用

- Q17：首期采用 Node.js 24 LTS 和内置 `node:sqlite`，实施时锁定核验通过的完整补丁版本与容器镜像摘要。接受调查版本 Node 24.21.0 中该驱动仍为 release candidate、尚非稳定 API 的取舍；升级前验证事务、整数精度、备份恢复和错误处理。若验证发现无法接受的问题，再评估切换至 `better-sqlite3`，不预先维护两套驱动。[版本对应的官方文档](https://nodejs.org/download/release/v24.21.0/docs/api/sqlite.html)
- Q18：数据库先采用应用主线程内一个业务连接与短事务，战斗演算仍在独立线程池。同步数据库调用会暂时阻塞请求处理，因此验收必须覆盖交易、战斗结算、后台统计及备份同时运行时的响应延迟；先优化慢查询、索引和批次，仍不达标再增加数据库工作线程。备份产物校验使用独立只读连接，不改变生产业务只有一个连接的约定。
- Q19：自动备份初始频率为每 5 分钟一次，最新可用异机恢复点落后 10 分钟时提前告警，超过 15 分钟按 Q5 暂停业务写入。上一轮未完成时不并发启动另一轮；频率须用实际数据量和网络验证，不能仅凭定时任务按时启动判定达标。若不能满足目标，调整备份方案或资源，不静默放宽目标。
- Q20：采用 SQLite 在线备份生成一致副本，再由 restic 去重、在上传前加密并上传至 S3 兼容存储。每个恢复点仍能还原完整数据库；锁定 restic 版本并维护仓库检查和恢复工具，验证实际节省量、备份及恢复速度。restic 不直接备份正在写入的数据库文件，不替代已确认的恢复演练。[restic 官方文档](https://restic.readthedocs.io/en/stable/040_backup.html)

## 已确认的内部留存

- Q21：资产与成长的业务流水、完整结算凭据默认从每笔业务成功提交起保留 1 年，期限可通过部署配置调整；到期后不再承诺查询完整收支细节。防重复扣款、发奖所需的最小操作身份、参数摘要与终态继续按已确认规则保留，不能随流水删除；未完成操作和仍被业务引用的记录不因到期清理。
- Q22：内部战斗复现材料默认正常正式战保留 90 天、模拟战 30 天、故障取消后 30 天，从成功结算或正式取消时起算；进行中的战斗始终保留原输入。管理员提前清理玩家可见战报，不提前删除仅供内部诊断的复现材料。所需引擎、内容和历史素材版本保留至依赖它们的在途操作、复现材料、可见战报及备份均不再需要；到期后可以保留结算凭据，但不再承诺重新演算。

## 已确认的时间异常处理

- Q23：运行中检测到服务器时间突然前跳或回拨至少 5 秒，或校时检查无法确认时间可靠时，暂停玩家、后台和管理业务写入，保留查询、备份及诊断；校准并由运营确认后恢复。重启前也核验时间，不能靠重启清除异常。正常的小幅渐进校时继续运行，业务时刻不倒退；校时服务器短暂不可达但本地时间仍在可信范围内时只告警。接受时钟故障导致停服的代价。
- Q24：正常维护、进程停机和保护性暂停的可靠现实经过时间继续计入体力恢复、冷却及其他现实期限。恢复时按原公式计算体力并封顶，冷却照常经过；拍卖按原截止结算，Boss 仅检查恢复时当前条件。时钟异常修复后，仅当原保存基准与当前时间都可靠时按差值计算一次；原基准损坏或无法核实则交运营按证据修复，不猜测补发、不扣减体力、不自动重置期限。

## 已确认的查询回执、日志与告警

- Q25：删号结果查询回执保留 7 天，仅供持有原回执令牌的人确认那次删除；战报过期/已清理状态回执保留至战斗完成后 1 年，只说明原记录状态，不恢复详情，模拟回执仍须鉴权。期限结束后提示记录不可查询。防重复结算的内部最小凭据，以及仍被历史交易等引用的已删除身份，继续按各自规则保留，不随查询回执清理。
- Q26：应用与反向代理运行日志默认保留 30 天，自动轮转清理，与管理记录、业务流水分开。只记录排障所需的请求编号、路由类型、状态、耗时、错误类别和必要内部业务引用；不保存密码、恢复码、会话令牌、完整请求正文、原始 IP，不另建 IP 历史轨迹。短期限流可临时使用来源 IP，最近成功登录 IP 核查仍按已确认独立规则处理。
- Q27：部署时配置一个通知 Webhook，并设置服务器外存活监测。备份陈旧、数据库/磁盘故障、时钟异常和任务需人工处理等事件通知运营；同一故障去重并限制提醒频率，恢复后通知。外部监测发现整机或应用失联。只发送故障摘要与排查编号，不携带玩家凭据、IP 或战斗完整输入；通知平台在部署时选择，本轮不注册或购买服务。
- Q28：磁盘空间不足以安全完成后续写入和备份时进入只读保护，提前告警，到安全余量下限时暂停玩家及后台业务写入，保留查询及可执行的备份、诊断；已受理战斗不取消。安全余量按数据库、WAL 和备份临时文件实测占用确定。不能自动删除未过期战报、流水或有效备份腾空间；扩容或按既定规则清理后，核验数据库与备份状态再人工恢复。
- Q29：首期由 Caddy 统一提供 HTTPS、前端静态文件和反向代理，玩家经同一域名访问界面和 API。Caddy 管理证书及续期，Fastify 仅经容器内部网络接受代理请求；后端只信任明确配置的代理来源，不相信玩家自行提交的 IP 转发头。代理日志遵守 Q26，域名与证书条件在部署时配置，本轮不购买域名。[Caddy 官方文档](https://caddyserver.com/docs/automatic-https)
- Q30：灾难恢复后，由服务器管理者核对恢复报告并记录操作者，再手工开放业务写入。须确认旧服务器已隔离、版本与数据库匹配、新恢复代次和旧会话失效已落实、原待处理业务具备恢复条件，并验证新服务器可生成可用异机备份；报告列明恢复点和进度损失窗口。普通备份过旧保护仍可在新备份校验后自动解除，不能顺带解除灾难恢复、时钟或磁盘的人工保护。

## 已有约束与调查边界

SQLite WAL 使用服务器本地持久磁盘，一次仅一个写者；战斗演算与写事务分离，受理输入和随机状态、业务占用及执行代次持久化。恢复沿用原操作，租期到期不释放业务占用；取消必须确认无法完成且无成功结果。约 100 人在线仍是首轮负载验证目标。

应用与内容更新采用短维护、排空、兼容性检查和明确迁移。维护阻止新的玩家、后台及管理业务写入，既有排空与迁移按已确认协议处理；旧备份恢复与普通进程重启、发布回退分别设计。已受理清理任务保留原固定范围授权。

运行选型的官方事实已通过[核验 Node.js、SQLite 驱动与单机备份的官方运行约束](https://github.com/odradekk/hof_redux/issues/20#issuecomment-5765541544)独立调查并审查，详见[调查报告](../research/runtime-sqlite.md)。Q17–Q20 已确定运行时、驱动、初始数据库执行方式及备份方案；具体补丁版本在实施时核验锁定。SQLite 在线备份不等于单独复制运行中的主数据库文件，也不自动满足异机备份新鲜度或恢复目标。[SQLite 官方备份文档](https://www.sqlite.org/backup.html)

## 进程、持久目录与数据库边界

以下执行约束已随 Q31 完整契约确认。生产只运行一个可提交业务的后端实例，启动互斥与实例身份须能阻止误启动的第二实例同时调度；不把单机 SQLite 当作多个容器共享写入服务。普通进程重启、同库版本发布和旧备份灾难恢复是三条不同流程。

数据库整个目录挂载到 Linux 本机持久磁盘，包含 SQLite 管理的 WAL/共享内存文件；不可只挂载主数据库文件。备份工作目录、已完成待上传副本、版本执行物、代理证书状态和必要运维配置各有明确持久位置及权限。数据库、备份明文副本、秘密和日志均不位于公开静态目录。容器替换不删除持久状态；生产库不使用网络文件系统。

应用业务连接开启并读回校验 WAL、`synchronous=FULL`、外键及有限忙等待。业务使用短 `BEGIN IMMEDIATE` 事务，取得写入机会后重新读取依赖并校验；随机业务结果、资产、状态、流水和终态按既有契约一起提交。事务内不执行网络、密码哈希、战斗演算或跨线程等待。忙等待不得长时间阻塞主事件循环；具体上限通过组合负载锁定，短请求的等待失败与 Q15 已受理长操作的恢复重试分开。

所有整数在存储、计算和 HTTP 边界有明确范围与转换，不能因 SQLite 64 位整数转换成 JavaScript `number` 丢失精度。启动核验 Node 与实际 SQLite 版本、编译能力和迁移版本；容器系统的 SQLite 命令行版本不能替代驱动实际版本。锁定的版本须包含已知 WAL-reset 修复，不使用撤回版本；升级重跑事务、整数与备份契约验证。

主线程仅执行受控数据库工作。副本完整性检查、文件摘要、压缩、加密和上传交给有界的辅助执行环境，不占用业务连接，也不把同步大文件处理放在请求主线程。校验连接只读已完成副本；备份源沿用业务连接的在线备份 API，若实测不满足响应目标，按 Q18 先优化再调整数据库执行位置，不擅自增加多个生产写连接。

## 受理、执行权与恢复

受理前取得可用战斗处理名额，再在短事务内确认资格、固定输入、版本、随机状态及占用。名额竞争失败不产生半受理或保存配置；受理成功后即使线程启动失败，原操作仍可恢复。战斗线程无数据库写权限，结果只能由应用按操作终态、执行代次和玩法依赖验证后提交。不同 Boss 的占用、竞技全榜占用及账号正式/模拟占用继续各自生效。

执行权使用持久执行代次和有期限的领取记录，心跳仅续当前执行者的权利。租期到期允许接管原操作，不能自动释放成本、账号、角色、装备、Boss 或榜单占用。接管先使旧代次不能提交；不以 HTTP 断线或线程未响应证明原事务失败。恢复及管理员重试都先查原终态，已完成则返回原结果。临时故障的重试次数与下一次可尝试时间随原操作保存，重启不重置次数；三次重试指初次失败后的三次额外尝试。

确定性错误的独立复核与临时故障重试分开记录。复核必须使用完全相同的规则、输入、随机状态和确定性预算；同一诊断再次出现才符合 Q14 自动取消条件。结算结果未知时先查数据库，不得因演算异常覆盖已提交成功。取消与成功争用同一个终态转换；取消后无本场胜负、收益、实际成本和成功冷却，受理时已经保存的战术或记忆队伍仍保留。

程序保护、执行租期和单次执行超时分别处理：

| 限制 | 依据与作用 | 达到限制后的结果 |
| --- | --- | --- |
| 正常行动上限 | 已确认的玩法模式规则 | 按战斗契约产生正常结果 |
| 确定性执行预算 | 对调度转换、效果展开、目标/段处理、单位创建及事件逐类计数；预算纳入版本及本场复现输入 | 演算错误，可按 Q14 复核，不能伪装平局 |
| 执行租期 | 当前执行者心跳和代次 | 可接管原操作，不解除业务占用 |
| 单次执行超时 | 目标硬件上防止线程卡死的外层限制 | 隔离/终止该次战斗执行，按 Q15 恢复，不直接取消或判负 |

实施先分析正式内容及处理器的机制边界，包括召唤、非行动计数步骤、蓄力/咏唱、失败行动、多目标及多段效果；为合法输入推导预算或提供覆盖最坏组合的保守上界及依据。不能只按普通五人样例定值，也不能为迎合预算删去正式内容。无法建立边界、出现合法输入耗尽预算或发现非终止规则时阻止发布，回到内容/保真契约解决，不静默改玩法。租期、心跳、线程数和超时在慢速及目标硬件验证后锁定；生产不允许无界线程、无界排队或无限循环重试。

## 调度、清理与 WAL

定时器只负责唤醒，业务是否到期仍在事务内按保存状态判断。拍卖到期和业务唯一结算不依赖一次定时回调是否恰好执行。后台任务逐项/逐批短事务，失败不阻塞无关对象；固定范围的管理清理任务按原授权续行。重启按数据库状态恢复扫描，错过的扫描不按次数堆积补跑；Boss 只检查当前条件。

到期数据默认每小时触发分批清理，批大小按负载验证限制，可中断续行；只读保护期间不进行业务清理。查询在到期时刻即执行可见性限制，不等待物理清理。IP、会话、回执及私有模拟均先遵守原权限和期限。保留期限的部署默认变更用于新记录，既有记录的固定到期时刻不静默改写；明确允许的管理提前清理仍走具名流程。删除查询回执不删除最小幂等凭据，账号删除后的身份仅在无历史及业务引用时才可清理，内部身份从不复用。

WAL 保留默认 PASSIVE 自动检查点作为初始方案，监控增长、检查点受阻、长读和提交延迟。统计不持有无限期读事务；需同一时点的统计采用有界一致读，验证其与备份、结算的组合负载。停机排空后可尝试收缩 WAL；检查点失败不等于需要删 WAL，禁止手工删除仍在使用的 WAL/共享内存文件。磁盘安全余量包含生产库、WAL 峰值、备份工作副本与校验空间，不能仅按主数据库大小判断。

## 备份发布与灾难恢复

1. 在短事务中写入备份身份、恢复代次、递增序号、可信应用时间及应用/内容/迁移版本；提交后从同一打开连接启动在线备份，写入新的工作文件。该时间是副本覆盖范围的保守下界，不是上传时间，也不是 SQLite 自动提供的精确提交时间。
2. 完成一致副本后，在副本上校验标记、数据库结构、外键和版本清单，保存文件摘要。每轮生成完整副本；分批复制不等于只复制变化数据。备份过程有总时限和有界重试；失败文件不能覆盖最后成功产物，也不能与下一轮并发操作同一工作路径。
3. 将副本及恢复清单交给 restic，使用稳定的逻辑路径/分组和新恢复点身份，避免临时文件名改变导致保留策略失效。备份命令须完整成功；退出码 3 的不完整快照不能成为可用恢复点。读取远端快照清单并核对本轮文件、标记及版本引用后，才更新已验证恢复点。每轮上传/清单核验、每日实际下载校验和每月完整演练分别留记录，不能彼此冒充。
4. restic 仓库数据检查与到期清理遵守其锁与引用关系，不手工删除共享数据块；安排有界维护，避免清理长时间阻塞 5 分钟备份任务。高频恢复点保留 24 小时、每日一份保留 30 天；所选恢复点依赖的应用、引擎、内容、素材和配置必须同时可取回。恢复密钥在服务器外另存，不能只存在于同一备份中。定期实测仓库占用和下载费用，不假定去重率。
5. 监控依据是最新可用远端恢复点覆盖的可信时间，10 分钟预警、超过 15 分钟停写。启动不重新赠予 15 分钟宽限；只有本地文件、上传启动或新对象名称均不算成功。暂停业务期间可继续必要备份和控制元数据写入，以便恢复保护；这些写入不得触发游戏结算或消耗资源。

灾难恢复先隔离旧服务、旧存储写者和执行者，下载至独立工作目录，验证摘要、数据库完整性/外键以及应用、内容、配置与迁移版本。不得覆盖仍被打开的生产库。为恢复实例创建新的恢复代次，隔离所有旧会话、旧页面请求和迟到执行结果；恢复代次不能仅使用会随备份回退的自增值。恢复后新建的内部身份也不得与回退窗口内已产生的身份碰撞，不能按可复用名称拼接旧业务。

开放前重新执行当前到期与权限检查，核对备份内在途战斗和拍卖能按原状态恢复；不为补算而重抽战斗或回填击杀时间。管理员身份重新授权，玩家凭据及生命周期按 Q7 接受回退。恢复报告列出实际恢复点、可能损失窗口、版本、校验结果、未完成业务、隔离情况和备份链路状态。按 Q30 由服务器管理者核对后手工放行；开放前核查业务可恢复性不要求在保护期间先提交战斗/拍卖结果，放行后立即恢复和扫描补结算，竞价始终按原截止拒绝迟到请求。

## 时间与暂停的统一入口

同一业务事务只取得一次已校验的当前时刻，跨模块共用。保存绝对 UTC 时刻，地图/Boss 的当地窗口再用有效部署时区解释；启动解析并校验统一时区，不接受无效名称后静默退回另一时区。浏览器时钟不决定资格、截止或结算。

进程内使用不依赖日期的区间计时检查服务器时钟跳变及安排等待；该计时不能跨重启证明停机时长。持久基准与宿主校时状态共同用于启动核验，正常重启不改写玩家恢复基准、冷却或截止。连续的小幅异常不能通过每次重置比较基准绕过 5 秒保护；正常渐进校时与异常累积须经故障注入区分。校准当前时钟不能证明过去的错误时间已经修复，涉及坏基准时保持受影响写入关闭并按证据修复。[Node 区间计时](https://nodejs.org/docs/latest-v24.x/api/process.html#processhrtimebigint)、[chrony 校时状态与误差说明](https://chrony-project.org/doc/4.8/chronyc.html)

维护、备份过旧、时钟异常、磁盘不足及灾难恢复分别保存暂停原因。只有相关原因均已解除才开放业务；清除一个原因不能顺带清除其他原因。系统保护覆盖玩家、定时任务、管理修正与页面访问触发的写入。运行控制和恢复检查有独立入口，只允许核查、修复运行条件及必要控制记录，不借此买卖、发奖或跳过管理权限。数据库不可用时拒绝业务写入，不能把未保存的控制变更报告为成功。

时钟/磁盘的人工放行验证相应问题已解决，记录操作者、原因和检查结果；满足近期密码验证的管理操作仍遵守运营契约。网页或身份验证因故障无法安全使用时，由服务器管理者通过受控本机恢复流程处理并留记录，不能提供匿名 HTTP 放行接口。

## 维护、发布与停止流程

发布前先在副本演练迁移及新版本，生成明确的兼容性和影响报告；涉及拍品时先执行交易专题要求。进入持久维护状态，禁止新玩家、后台和管理业务写入；只允许既有操作排空及批准的发布控制/迁移。备份、时钟或磁盘保护同时存在时，保护限制优先，不能借维护排空继续业务写入。

按顺序排空短操作和已受理战斗、隔离旧执行者、形成并验证迁移前异机恢复点、在稳定状态重跑兼容性检查、执行具名迁移、验证目标应用与内容、整体切换前后端及素材、再开放服务。排空达到运维等待上限时本次发布失败并保持维护；不能为升级自动取消合法战斗。运行控制状态与发布阶段持久保存，进程重启不自动当作发布成功。

每项迁移明确事务边界、可重复执行的身份、中断恢复方式和验证；失败保持停写。数据库事务尚未提交时按事务回滚；已提交后目标应用失败，则先诊断并前向修复，只有旧应用与当前数据确实兼容才允许回退。不能把迁移前数据库备份自动覆盖当前库；需要丢失进度的恢复必须走灾难恢复流程。

正常停止先拒绝新请求和新任务，等待短事务及受控任务到安全边界，再关闭数据库连接并退出。容器停止宽限经停机演练确定；强制终止后的未完成操作仍按原身份恢复。不得通过强杀正在执行原生数据库调用的线程来取消单个请求；战斗工作线程与数据库执行边界分开。

## 认证、代理与运行检查

Caddy 只转发到受限的应用内部入口；限定可信代理地址/网络，清理来自公网的伪造转发信息，验证 HTTPS 协议和真实来源识别。Cookie、CSRF/Origin 校验遵守账号契约；静态站点和 API 同源并不免除 CSRF 防护。[Fastify 可信代理说明](https://fastify.dev/docs/latest/Reference/Server/#trustproxy)

Argon2id 在数据库写事务外执行，使用有界并发与等待；取得事务后重新核验凭据/生命周期版本再签发会话。注册、登录、恢复、管理验证与普通请求按类型设置限流，结合账号与临时来源维度，避免仅按共享 IP 永久封锁。参数至少满足账号契约下限；哈希库、队列大小和请求阈值须在目标镜像验证后锁定，不声称目前已通过 100 人认证压力测试。

应用健康、数据库可访问与可接受玩家写入是不同状态；对外只暴露最小状态，后台诊断显示具体暂停原因、备份年龄、WAL/空间、任务阶段和版本。秘密用受权限保护的文件等方式注入，不写入镜像、仓库、公开健康页或日志。Compose secrets 只负责容器内注入，不能替代服务器外恢复密钥保管。

## 实施定值与上线门槛

本专题确定运行方式和失败边界。以下数值依赖尚不存在的新实现及目标服务器，在实施中产出可审查记录并由[整体验收](https://github.com/odradekk/hof_redux/issues/18)锁定，未通过不能上线：线程及名额、确定性预算、租期/心跳/执行超时、数据库忙等待与清理批次、磁盘余量、校时可信度判定、认证并发/限流、告警频率、停止及维护等待上限。它们不能改写已确认的玩法、暂停阈值、保留期限、15 分钟恢复点目标和 2 小时恢复目标。

| 验证 | 必须保存的证据与通过条件 |
| --- | --- |
| 版本与数据库 | 最终 Node/SQLite、镜像摘要、操作系统/文件系统/磁盘；事务、整数、FULL、外键、忙等待及 WAL 检查通过 |
| 约 100 人组合负载 | 实际硬件、数据量、操作比例、频率、延迟分位数、错误率、事件循环及写入等待；叠加交易、战斗、Boss、拍卖到期、后台统计、备份和清理，拍卖正常结算目标通过 |
| 战斗边界 | 所有正式可达机制、召唤和非行动计数路径有边界依据；合法极端输入不被保护误伤，故意植入的循环产生稳定错误，冻结线程与迟到提交被正确隔离 |
| 故障恢复 | 受理/结算各阶段中断、响应丢失、进程重启、数据库忙/不可用、恢复与取消竞争；无重复收费发奖、部分提交或裸解除占用 |
| 备份与资源 | 持续写入、慢上传、中断、损坏副本、不完整 restic 快照、仓库维护阻塞、长读及低磁盘；只有真实有效恢复点更新新鲜度，保护与告警生效 |
| 异机完整恢复 | 实际下载、解密、数据库与版本校验、新代次、旧会话/请求隔离、待处理业务恢复及新备份链路；人工开始后 2 小时内恢复，正常可用远端恢复点满足 15 分钟目标 |
| 时间与控制 | 正常校时、前跳/回拨、重复小幅异常、跨重启、夏令时、复合暂停；不重复恢复体力、不重开已截止拍卖，人工保护不会被自动检查或重启解除 |
| 发布 | 排空失败、迁移中断、目标版本失败、兼容与不兼容回退、旧执行物保留；失败保持明确版本和停写状态 |
| 清理与入口 | 到期权限及时失效、回执与内部去重分开、固定范围清理续行、代理来源验证、认证容量、日志不泄露敏感输入；告警实际送达及外部失联发现通过 |

不通过时先修复、调整资源或按 Q18 调整执行位置；不能把目标写成已达到，也不能默许上线后再补备份恢复和并发正确性验证。
