# 实施阶段、纵向切片与交付检查点

状态：已确认。Q1–Q6 逐项决定及 Q7 完整路线均经用户确认。对应[确定实施阶段的纵向切片与交付检查点](https://github.com/odradekk/hof_redux/issues/19)。本轮定义实施路线，不开始生产应用开发，也不创建实施任务；规划完成不表示游戏已实现或通过验收。

## 已有决定与规划边界

- 沿用既定顺序：最小可玩闭环 → 完整养成、装备与地图 → 交易、竞技与世界 Boss → 其余正式功能 → 整体运行验证。每个阶段交付可以操作的流程，不先把所有数据库表、所有接口和所有页面分别做完再集成。
- 最终覆盖范围不变，沿用[保真基准](../legacy/fidelity-decisions.md)的能力和内容清单，以及各专题批准的新能力与差异；核心循环可玩不等于完整重写完成。
- [完整验收契约](acceptance.md)约束最终完成。功能对应的规则、权限、事务和恢复随功能验证；最后阶段负责全量组合及运行门槛，不表示此前可以省略测试或等到最后才发现无法恢复。
- 技术栈、模块边界、内容发布、手机交互和接口已确认，路线不重新选型。具体依赖补丁版本、数据表与测试工具按批准契约在实施时核验；不能把未核验选择写成项目现状。
- 原型独立保留，生产界面按 Vue 技术基线重新实现；`old_hof/` 仅用于规则、内容和素材取证，不导入旧运行资料或凭据。

## 已核实的前置关系

- [账号契约](accounts.md)规定注册和首次建队分开，内部身份不复用；首次建队前不开放正式玩法。注册、会话、初始资产和角色必须真实持久化，不能靠浏览器状态模拟账号。
- [地图冒险](adventure-flow.md)确认 gb0 为无条件开放的“哥布林（最弱）”。旧 `data.land_info.php` 中该地图抽选怪物 1000/1001；旧 `data.base_char.php` 提供战士、法师的初始装备、技能和默认战术。首批实现须核对这些内容的实际依赖，不能把未实现效果当作无效果运行。
- [内容发布契约](content-release.md)要求引用、类型和处理器合法。阶段内容可以分批实施，但每批可执行内容必须有明确来源和完整运行依赖；未知处理器不能用空函数掩盖，阶段子集不等于正式完整内容已交付。
- [账号契约](accounts.md)允许解雇到零角色；[交易契约](trading.md)保留单次打工。解雇、打工与招募必须能形成可恢复流程，不能在阶段试用中制造无法继续的账号。
- [展示契约](public-information.md)规定正式战报公开、模拟私有。第一阶段的普通战报即遵循正式权限，不因尚无 Boss/竞技战报而改成私有；受控测试环境的访问限制与游戏内战报可见性分开。
- 拍卖、竞技、Boss 各自包含共享状态、占用和恢复；不能只把普通冒险换一个敌人或页面名即宣称完成。增加这些状态时，同步纳入账号/角色删除、内容更新及管理操作的保护。
- [运营契约](operations.md)的具名管理操作依赖独立管理员身份、权限、原因、记录和必要的近期验证。需要提前交付的诊断与业务恢复也须遵守这些约束，不能以临时裸数据库编辑器替代。

## 每阶段的贯通流程和完成证据

各阶段使用同一生产实现逐步扩展。受控试用不放宽已实现功能的规则；缺少依赖时不开入口，不提供伪成功按钮，也不临时修改价格、成长、掉落、冷却或权限。阶段子集在构建和报告中明确标识，不改写内容的正式开放状态来冒充完整发布。

### S1：真实账号到一次持久冒险

输入为已批准的内容、战斗、事务、账号、界面及运行契约。先确定 gb0 和初始战士/法师的内容与机制依赖，使用真实 JSON、素材来源、稳定标识和校验；建立最小可运行工程与检查入口后，立即按流程贯通存储、模块、HTTP 和界面，不先建设覆盖未来全部系统的框架。

- 玩家可注册、登录、完成首次建队，招募战士/法师并选出 1–5 人；初始角色、装备、技能、阵位和默认战术按真实定义。账号、角色和装备使用不复用的内部身份。
- 账号基础包含恢复码签发、使用与重新签发、改密及会话撤销、多设备登录/退出、名称校验、注册容量与首次建队门槛。不能先发放一个尚不能用于恢复的凭据；尚未交付的队伍改名、自助删号和偏好入口明确留在 S4。
- 普通冒险从资格校验、遭遇抽选、体力预留到工作线程演算，再原子提交成长、掉落、流水和战报。提供余额、成长和所得物品的真实只读查看；手动加点、技能学习、战术编辑和换装到 S2。
- 手机可选成员、看到处理中/待核对状态、查看公开普通战报及静态阵型/逐步 HP/SP，重新登录后查询同一结果。未知结果、原请求查询与封闭、旧页面版本拒绝等所需协议随入口实现。
- 使用 SQLite WAL/FULL、单业务连接、受控工作线程和持久操作记录。验证重复请求、受理/结算边界断线或重启、迟到执行者和事务失败，不能重复扣发、重新抽取或丢失已受理业务。
- 战斗恢复从本阶段就包含有限重试、确定性错误复核及符合条件的故障取消；需人工核查的操作保留原记录和占用。重试耗尽、受理满 5 分钟未完成及确定性错误取消按运行契约告警，具备可送达运营的基础 Webhook 通知并验证送达。配套最小的具名诊断、恢复/取消入口及其独立管理员身份、权限、近期验证和审计，不能把解除首阶段故障的唯一办法留到 S3，或靠直接修改数据库清除占用；完整后台仍按后续阶段补齐。
- 可从空库启动、关闭重开后继续，也可生成一致备份并在隔离目录恢复；具备基本维护、迁移/版本核对和故障诊断。远程试用走同域 HTTPS；此时不宣称异机灾难恢复目标已经通过。

交付证据包括上述实际操作、规则及事务测试、备份恢复结果、构建/内容版本和手机布局检查。用户从空账号走完建队、招募、冒险、重登与战报阅读。页面中的材料和装备必须与结算后数据库一致，不能只显示临时奖励文本。

### S2：培养、材料和再次冒险

基于 S1 的持久闭环，补齐正式招募模板、成长/加点、角色改名/解雇、重置、技能学习、转职、主备战术、阵型与保护、记忆队伍、完整背包、装备/卸装、制作与精炼。补齐普通冒险正式地图和单人/团队模拟；未开放定义仍保留且不可进入。

商店买卖和单次打工随本阶段交付，严格数量和整笔事务生效。用户能完成“冒险得材料 → 制作/换装 → 保存战术并模拟 → 再次冒险”，也能解雇到零角色、收到退回装备，再通过体力恢复、打工和招募继续游戏。模拟战产生私有历史，不产生正式收益；草稿、服务器已保存战术、主备方案和出战成员不混淆。

内容提取与校验在本阶段补齐全量基线：15 职业、193 物品、268 唯一技能、147 怪物、24 地图和 90 制作输出，以及关联的条件、效果、素材和来源。完成全部正式可达机制处理器的规则验证；Boss/竞技特有的流程集成和运行实例在 S3 完成，不能据此提前开放入口。按内容发布契约归档的旧未实现内容只保留已知定义和来源，不补造机制；正式可达内容未实现或引用未闭合时，本阶段不能以数量齐全代替完成。

补齐加密异机备份、版本/配置恢复材料、备份陈旧停写、告警和可用恢复点验证；实际使用服务的选择、授权和凭据准备按实施任务处理。未配置或未实际验证时如实标为未完成，不能用本地备份代替该阶段的异机能力。

交付证据覆盖养成公式、装备实例和材料收支、精炼正常负面结果、占用冲突、非法配置、草稿冲突及两种模拟；用隔离内容包验证已有机制的新物品、职业与怪物通过数据加入。用户重点试用角色切换、换装、编辑/保存/测试战术和零角色恢复。负载采样和数据生成可从此时准备，不提前声称最终 100 人验收通过。

### S3a：拍卖

基于 S2 的资产、装备、商店与异机恢复能力，交付会员资格、列表/历史、上架、竞价、超价退款、延期、到期成交/流拍。后台按既定频率结算，离线买卖双方正常收到钱物；截止后的迟到请求不得竞价，维护不自动延期。

复用 S1 的独立管理员身份、会话/近期验证和审计，增加必要账号/资产/拍卖查询，以及取消退款、结算诊断/重试和全服/按物品暂停新上架。每项操作核对权限并填写原因，不得绕过授权用原始表编辑替代业务操作。

以多个账号验证争价、退款、唯一交付、上架重复请求、结算重启、维护和受影响内容更新。用户从卖家上架到买家竞得/被超价，再核对双方钱物及管理取消结果。账号删除保护的规则与测试随拍卖状态加入，即使玩家删号页面尚未交付。

### S3b：竞技场

在已验证的战斗和管理基础上，交付公开榜单、竞技名单、主动挑战、防守及正式战报。按批准规则处理档位、选对手、最新角色快照、48 小时名单限制、胜负冷却、空榜和榜外入榜，不用简单互换相邻名次替代。

同步交付竞技查询、异常诊断、无效账号移榜、顺序/战绩修复及有依据的名单恢复。全榜只有一场在途正式挑战；删除角色、榜单重排和删号保护与此一起完成。

验证互相挑战/争同一名次、第三人删号或管理修复竞争、受理后成长换装、重启恢复及取消无收益。用户用多个账号设队、挑战和查看守方战报，确认名次、战绩及等待提示可理解。修复不能伪造战斗或重置冷却。

### S3c：世界 Boss

交付 12 种 Boss 各一个开服实例、精确已提交 HP/SP、挑战、随从、共享状态结算与按条件持久复活；按当前账号数计算数值的口径、挑战资格、账号共用冷却和击杀提交时点均按契约执行。

配套定时/访问复活检查、实例与轮次诊断、原挑战恢复及有依据的故障取消。常规后台不增加任意改血、强制击杀或提前复活按钮。

验证同 Boss 竞争、不同 Boss 的受理机会、唯一击杀收益、演算/提交故障、特殊时段及停机后的当前条件检查。用户连续挑战并看到他人已提交结果，复盘随从/召唤单位完整战报；不能把敌方统一裁成五人。到此完成四种战斗模式的共同规则与各模式差异集成验证。

### S4：完整玩家功能与运营闭环

基于前三阶段的真实账号、资产和共享义务，补齐队伍改名、偏好、自助删号、两类留言、公告、公开资料、图鉴、手册/教程、城镇入口和可配置论坛链接，以及完整玩家/管理查询页面。早期已交付的公开普通战报、私有模拟及竞技/Boss 战报继续保留，不推迟至此才实行可见性规则。

补齐全部运营能力：停用/恢复和具名删号，资产、角色、装备与名称修正，完整统计，一致性诊断，有限 IP 核查，公告/留言管理，战报批量清理，生效配置/版本和内容只读核对。各项遵守预览、原因、敏感验证、并发保护和追加审计；旧任意文件编辑不复刻。

补齐时钟/磁盘保护、复合暂停和人工放行、日志与数据到期清理、版本依赖留存、外部存活监测、每日备份验证、灾难恢复工具和发布/回退流程。已有记录自创建就带正确时间、身份与版本，不能直到 S4 才补猜历史。战报到期权限随战报实现；物理清理和完整后台在此补齐，不能延长此前记录的玩家可见期限。

逐项核对旧能力、内容和批准差异都有实现、替代或不迁移依据，所有正式机制有测试入口。用户执行主要账号、社区、资料及管理流程，尤其是有未结义务时删号、名称复用、管理员修正和批量清理。S4 完成表示功能覆盖完成，仍不等于稳定版或已批准公开运营。

### S5：全量验收与交付

输入是 S4 完整候选版本、覆盖清单、各阶段已执行证据、测试数据工具、部署/恢复步骤和实际环境。按[验收契约](acceptance.md)执行全部门槛，包括一年等价历史数据、100 人常态与八小时稳定性、争用峰值、认证/管理负载、故障注入、真机/浏览器范围、完整异机灾难恢复及内容发布/兼容回退演练。

按[运行契约](runtime.md)实际锁定线程数、名额、预算、超时、重试/租期、批次、轮询、认证并发与磁盘余量等参数，记录选择依据和实测结果。故障修复回到相应实现任务，复跑受影响场景；不能通过减少玩法、缩短留存或降低已定目标使结果通过。

## 依赖、并行与反馈

七个集中交付点顺序为 S1 → S2 → S3a → S3b → S3c → S4 → S5。只有用户确认某交付点，才将它标为完成；等待反馈可继续独立准备、内容取证、测试工具或不依赖反馈的工作，不提前宣布后阶段已经验收。

内容提取/素材映射、公式证据、测试数据准备和界面展示可在输入明确后并行；必须使用共享定义和已确认模块操作。涉及同一事务协调、账号身份、操作状态、迁移或公共接口时先明确归属与契约，再划分任务，不让不同代理各自维护一套资产/会话/恢复状态。先完成一个真实纵向流程，再抽取确有复用需要的能力，不预建通用插件平台。

每次交付使用固定构建、内容和数据库版本，提供准备好的试用环境、可恢复测试数据、操作清单、已执行结果、未执行项和限制。原型代码评审不能作为生产界面验收；早期就验证相应手机布局和可操作性，有条件时安排真机试用，真实设备尚未覆盖的部分明确登记，最终完整真机范围不能延期越过 S5。

反馈按其实际影响处理：违反已批准契约的是缺陷，修复并复验；无法从证据确定的规则差异回到决策，不让代理猜测；新增玩法或改变批准范围另行确认，不混入普通修复。每项阶段完成结论附用户确认和证据位置，未执行不写成通过。数据重置先说明对象与损失，遵守项目对破坏性操作的授权规则；测试进度不继承不等于可无说明地删除。

## 交给实施任务拆分的规格

本路线已完整确认，可据此和各专题契约进入 `to-tickets`；具体拆分仍按该技能先审阅再发布，本轮不创建开发票。优先细化 S1 至可以实施的粒度，后续阶段保持明确交付范围和依赖，临近实施时再细化；不得用一张“重写游戏”票替代全部工作。

每张实施票至少包含所属交付点、可观察结果、范围外事项、能力/批准差异与契约链接、完整的存储至界面路径、依赖及验收方式。任务应能在单次代理会话内完成并留下可接手结果；过大时按可验证的业务流程继续拆，不按全部数据库/全部接口/全部页面分成三张孤立任务。必要的工程初始化或数据校验工具可以独立成前置票，但须说明服务于哪条流程与如何验证，不能长期只有基础工程而无可玩结果。

GitHub 使用原生依赖，区分真正的数据/接口前置与可并行准备；阶段顺序不意味着所有任务都机械串行。`implement` 接手具体批准任务，使用已有契约、规则证据与阶段验收表；发现新的产品决策时反馈到规划，不能借实现补齐未授权范围。提交、推送、PR、合并和部署遵守当时授权，本路线的连续推进决定不自动授权生产发布或购买服务。

本路线不预估未经证实的日历工期。每个交付点根据已完成票、剩余依赖和真实验证情况报告进展；完整功能与运行验收均通过前，不用完成票数宣布稳定版完成。
