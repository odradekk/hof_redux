## 已确认的行为

- Q1：同账号同时只处理一场正式战斗。计算和结算期间，本场角色不能加点、转职、改战术，所用装备不能更换、精炼或出售；其他不冲突的操作可以继续。读取战报不占用角色或装备。
- Q2：断线后继续处理已受理操作，重连取得原结果；重启优先恢复原操作并沿用原随机输入，确实无法完成时取消并释放预留。正常战败和行动上限仍收费，系统故障不损失资源。同一次操作不重复扣费、发奖或重新抽结果。
- Q3：旧页面不得覆盖已更新的配置。版本冲突明确提示，界面保留未提交内容供核对，不自动用新版本号重发旧配置。
- Q4：实际金钱/体力收支、物品流转及角色成长保存业务流水，与业务变化在同一事务中提交。流水保留期限在运行方案中确定。
- Q5：体力先预留、成功结算时扣除。预留仍计入余额及恢复上限，故障取消只释放；接受与旧开战即扣不同的时点，满体力预留期间不腾出恢复空间（LEG-19）。
- Q6：确认本文件的完整状态归属、跨模块命令、短事务、操作身份、流水、战斗恢复与结算契约，以及明确交由后续专题确定的边界。

## 状态归属与身份

同一事实只有一个持久化权威来源。表结构、ID 生成算法、驱动和 ORM 留给实施设计，不能据此省略下面的不变量。

| 模块 | 管理的持久状态与身份 | 对外操作与协作 |
| --- | --- | --- |
| 账号 | 账号 ID、登录凭据、会话、账号生命周期与访问资格 | 注册、登录/退出、变更账号信息、撤销会话、删除协调；不拥有余额或角色成长的写入逻辑 |
| 角色与编队 | 角色 ID/所属账号、成长/职业/技能、战术/保护/阵位、有序编队 | 招募、加点/重置、学习/切换、换装协调、转职、成长应用、角色删除；通过物品模块完成物品位置和成本变更 |
| 物品与资产 | 账号钱包、体力与恢复基准、堆叠材料、装备 ID/归属/位置/精炼/附加效果、资产预留 | 校验并消费/授予资源、装备迁移、制作/精炼、预留/确认/释放；禁止负余额与重复占有 |
| 战斗引擎 | 无账号或共享玩法的持久状态 | 接收完整快照并演算，返回计算结果；不持有数据库事务，也不直接发奖 |
| 地图冒险 | 冒险资格/进度、遭遇、普通战的受理与结算记录、模拟战调用 | 生成并固定遭遇、协调本场成本/成长/奖励；具体开放与资源规则归地图议题 |
| 竞技场 | 排名、防守记录/快照、挑战资格与冷却、竞技挑战记录 | 防守配置、挑战及排名结算；不把防守快照写回对手角色 |
| 世界 Boss | Boss 实例/复活批次、共享状态与版本、挑战资格/冷却、击杀与奖励凭据 | 挑战、共享状态提交、复活、奖励资格；旧 Union 不建立公会状态 |
| 交易 | 商店规则/必要库存、拍卖 ID、卖家、标的引用、价格、最高报价、到期与结算状态 | 购买/出售/打工、上架/竞价/到期结算；经资产模块转移钱物，不另存第二份钱包 |
| 社区与运营 | 留言/公告及其 ID、公共展示配置、管理操作记录、战报查询与可见性规则 | 发布/管理内容、查询与管理协调；涉及其他模块的修正走其公开操作，不直接改其表 |

只由内容定义或规则计算的图鉴、手册、可学技能、面板和地图开放条件，不仅为满足表格而新建持久状态。确实需要保存的进度须在对应玩法议题证明。

装备位置由物品模块管理：背包、角色主槽或拍卖占用等位置互斥；角色的槽位列表是这个关联的读取视图，不维护另一套独立可写的装备归属。角色模块的换装操作校验职业许可、承载和占槽，然后在同一事务中调用物品迁移。售卖/上架只能接受该业务允许的位置，不能借通用移动接口绕开换装规则。

业务模块可复用同一个数据库事务执行设施、操作记录和战报存储设施，它们不成为新的游戏模块。战斗所属玩法负责本场记录与结算，社区模块只负责战报查询/展示及其访问政策。战斗事件、结算凭据、业务流水是不同记录：分别说明过程、是否生效和状态如何变化。

## 事务与版本规则

1. 业务入口确定操作者身份、操作类型、请求标识和参数；页面提供的账号归属、价格、收益、随机种子和“已通过校验”标志均不作为可信依据。
2. 一次短操作只有一个最外层提交点。发起业务的模块协调所属模块的操作，在同一连接和事务中完成检查、变化、版本递增、流水与结果记录；被调用模块不能自行提交。
3. HTTP 入口和任务执行器调用同一个业务操作。调用方表达“购买这件物品”“结算这场战斗”，不能自行拼凑扣款、加物、写流水步骤。领域操作重复核验归属、状态、资格、余额和所占资源，不靠 UI 禁用按钮保证正确性。
4. 写操作使用短显式事务；实施时优先采用 `BEGIN IMMEDIATE` 在读取待修改状态之前取得写入资格。取得事务后重新读取最新值并校验。战斗演算、网络请求、文件导出和等待玩家输入不在写事务中进行。
5. 校验拒绝、系统/存储错误或未建模异常终止整个事务；已经定义的随机失败、战败、余额不足后停止连续精炼等游戏结果按命令契约提交。操作结果明确区分“拒绝执行”“系统错误”和“完成及其游戏结果”，不依赖一项成功布尔值混用含义。不能捕获中间存储错误后继续提交剩余变化；必须明确回滚、清理连接状态后才复用。数据库忙可有限重试整个安全事务，不能继续使用已经过期的读快照。
6. 配置修改提交其读取的预期版本。角色配置/成长、编队、装备、拍卖、Boss 等按实际一致性单元版本化，不以“账号任何字段变化”作为所有操作的冲突条件。复合操作检查全部依赖对象；字段细分不允许漏掉会影响资格的变化。
7. 金钱与材料使用最新余额做有条件的增减，绝不将战斗开始时的整份账号快照写回。收到拍卖款、留言或体力自然增长，不应使一场普通战斗无故失效。
8. 模块操作负责业务不变量，数据库唯一约束、外键和必要检查作最后防线。完整业务校验不能只靠数据库报错；违反约束也不得留下部分状态。

SQLite 可有多个读事务，但同时只有一个写事务；WAL 不消除写入竞争。读快照变旧后不能直接升级写入，`BEGIN IMMEDIATE` 可将写入竞争提前到事务开始；具体等待、重试和驱动错误处理须实施并验证。[官方事务说明](https://www.sqlite.org/lang_transaction.html)、[隔离说明](https://www.sqlite.org/isolation.html)

## 操作身份、重复提交与流水

- 一次操作由服务端校验后的操作者范围、操作类型和请求标识识别，并记录规范化参数摘要。相同身份和参数返回原操作状态/结果；同一标识换参数明确拒绝。换一个标识表示另一笔操作，仍必须通过业务限制。
- 完成身份验证和请求解析后，先识别已有操作，再验证新操作的余额、占用和当前业务版本。已成功购买的重试即使现在余额不足，也应返回原成功结果，而不是重新执行资格检查；结果查询仍须验证账号权限。
- 同一按钮点击的网络重试复用标识；尚无结果时返回“处理中”和查询凭据，不能显示为失败并自动另开一笔。不同设备的新点击不能单靠幂等键识别为同一次，仍由正式战斗占用、拍卖状态、余额及唯一结算约束保护。
- 短操作的业务变化、终态记录和流水在同一事务中完成，提交前不返回成功或随机结果。尚未持久受理且事务未提交的请求不承诺能恢复未保存的结果；重试不得重复已提交效果。
- 奖励还按业务来源建立唯一结算身份，例如战斗 ID、拍卖 ID 与结算类型。调用者更换请求标识不能绕过“一笔来源只结算一次”。系统到期任务使用同一业务来源身份。
- 完整响应与战报可按后续保留政策归档；在账号存续期间保留足以拒绝重复执行的最小操作身份、参数摘要及终态。清除展示记录不重置结算资格。已删除账号的新注册身份不能继承旧请求空间。
- 流水包含操作/结算来源、操作者或系统任务身份、账号/角色/装备引用、业务原因、实际前后值或变化量、服务端时间及必要规则版本。复合业务共享关联标识，同时为每个受影响账号及资产记录各自变化；拍卖总记录不能代替原出价者退款、买家扣款、卖家收入等分别归属的流水。错误修正追加具名修正记录，不覆盖旧流水。
- 状态表是当前状态来源，流水用于核查，不要求从全部历史事件重建账号。普通读取及未落库的体力预估不写收入流水；失败诊断与成功业务流水分开。

## 正式战斗的受理、演算与提交

正式战斗包括普通战、竞技挑战及世界 Boss 挑战。同账号的限制是业务占用，不是持有数据库写锁。所有会修改相关对象的玩家或管理操作都必须检查占用；后台也不能直接越过正在恢复的操作。

### 受理事务

验证账号可操作、无其他未终结正式战斗、玩法资格、出战成员和装备归属、所需资源可用。固定完整战斗输入、遭遇、内容/引擎版本和服务端生成的随机初始状态；建立本场唯一身份、待处理操作、出战角色/装备占用及必要成本预留，然后一起提交。

只有这一步提交成功才称“已受理”。输入包括恢复所需值，不能只留指向当前角色状态的引用。出战角色的持久修改、装备转移和新正式战斗在占用存在时被拒绝并返回当前操作；允许浏览、操作候补角色及不触及占用的资产。后续编队选择与本场已固定成员分开，不能修改已受理输入。

竞技防守队伍使用该专题规定的有效防守快照；被挑战者不因别人计算战斗而全账号冻结。共享 Boss 不使用全服长期数据库锁，其版本冲突策略归 Boss 专题。

### 事务外演算

短事务领取执行权并取得递增执行代次，再在事务外计算。进程重启或执行权到期后恢复同一操作；旧执行者只有持有当前代次才可提交，防止新执行者恢复后旧结果迟到覆盖。执行权失效不等于业务取消，也不自动释放角色、装备或成本。

恢复默认使用已保存输入与随机初始状态，不读取新装备或重新生成遭遇。共享状态已变化时先按对应模式协议判定原输入是否仍有效；不能把旧 Boss 快照覆盖回去，也不能悄悄将旧结果显示为新状态的结果。是否允许同一挑战在新共享状态上重新计算、如何使用固定随机输入，由 Boss/竞技专题明确；恢复机制本身不作这一玩法决定。

### 结算事务

同时验证操作未终结、当前执行代次、占用归属、角色/装备依赖版本、账号生命周期、共享玩法状态和唯一结算资格。这里的账号生命周期要求原内部身份仍存在且能承接已受理结果，不要求玩家仍可发起新命令；按[账号契约](accounts.md) Q10，停用或会话失效不取消既有业务，也不使原角色/装备依赖失效。规则验证要求受理时固定的内容/引擎仍可用、结果声明匹配本场版本；当前发布版本改变本身不是冲突，不能因此取消可恢复的旧版战斗。按模式把成长应用到角色，通过资产模块确认成本及增加收益，通过玩法模块改变 Boss/排名等状态；写入结算终态、战报/复现数据引用及流水，释放占用后统一提交。

结算基于最新钱包增减，不回写快照中的余额或装备清单。不受战斗影响的并发变化必须保留。战报可先产生内部计算记录，但只有成功结算的记录才能对玩家声明收益已入账；首期结算凭据和必要战报数据在同一数据库事务中保存，不依赖“提交后再写一个可能失败的文件”。

### 故障与取消

| 失败位置 | 可观察结果及恢复要求 |
| --- | --- |
| 受理事务提交前 | 无操作受理、无资源预留及角色占用；重试先查是否其实已提交 |
| 受理后断线或进程中止 | 操作保持待处理，恢复原输入；资源与角色占用仍关联原操作，不另开一场 |
| 演算错误、版本执行物无法恢复 | 在确认没有已提交结果后，原子转为取消、释放预留和占用；无收益、无实际成本及成功冷却 |
| 结算事务中失败 | 成长、成本、收益、玩法变更、流水与终态全部回滚，仍可查原待处理操作 |
| 提交成功后响应丢失 | 查询或重试返回同一成功结果；不重新演算、不再次发奖 |
| 取消与迟到结果竞争 | 以操作终态及执行代次决定唯一胜者；已取消结果不能入账，已成功不能走取消退款 |

取消是服务器对无法完成操作的终结，不提供玩家看结果后撤销挑战或通过断网取消成本的入口。管理员恢复/取消需走具名操作并有流水/审计；具体权限归运营专题。短暂数据库忙不是立即取消理由。恢复期限和任务频率归运行方案，但不能仅因租期到点就同时放行旧、新操作。

以上重启恢复以已提交数据库仍完整为前提。从旧备份恢复会回退业务状态，不等同于进程重启；恢复后如何拒绝旧客户端请求、隔离已失效执行者以及公布数据回退范围，归运行方案明确，不能用同一恢复承诺掩盖备份时间差。

## 资源预留与时间

钱包/材料的总量与预留量分开，可用量等于总量减去有效预留；预留、确认和释放都带原操作身份，不能被无关操作解锁。同一件装备的业务占用与其当前位置分开：战斗占用不把已穿戴装备变为“背包”，拍卖实际迁移到交易位置后不能继续使用。

体力保存余额和恢复基准时刻，按旧恢复比例与上限在业务需要时计算；不要求定时逐账号加体力。预留体力仍属于余额并计入恢复上限，成功结算才转为支出，失败仅释放，不以受理时的余额覆盖当前余额。预留阶段不额外制造恢复空间；用户在 Q5 已批准这一相对旧版开战即扣的时点差异。实际时间和旧公式的精度须保留，不把旧小数体力直接截成整数。

同一次短事务使用一个服务端时间。受理资格及价格等输入以该操作明确的业务时点为准；跨日、到期、恢复与停服边界由所属专题细化。冷却也区分处理中占用与成功生效：取消不能留下这次挑战的成功冷却，确认时点和计算起点按玩法专题确定。

## 代表性命令的原子边界

下表列出必须一起成立的变更；任一校验失败时没有部分业务效果。操作记录/流水的诊断性变化和自然时间经过不等于扣费。

游戏内的失败或停止规则与事务错误分开：连续精炼按旧顺序逐次付费、尝试，钱不足时停止并保留已完成结果。旧静态执行在随机精炼失败时停止且不放回原装备（`class.main.php:2172,2184–2196`），精炼页面亦提示“不过加工坏了我们不负责”（`:2127`）；按已批准保真基准保留这一装备损失，不自行认定为存储错误并返还。整批已执行的次数、支出和最终物品状态作为一个合法业务结果一次提交；数据库写入失败则整批回滚。不能为了“全部原子”擅自改成必须先付得起全部请求次数，也不能因随机精炼失败自动退款。

| 命令及协调模块 | 检查与必须原子提交的变化 |
| --- | --- |
| 招募：角色 | 招募资格/名额、价格、钱；扣款、新角色及初始装备身份/归属一同成立 |
| 属性加点/重置：角色 | 角色归属、占用、版本、合法属性/点数和成本；基础属性/剩余点/成本共同改变，战术超容量隐藏但不删除 |
| 学习技能、保存/切换战术：角色 | 对实际目标技能验证职业/等级/前置/点数；扣点与学习一起提交。战术当前/备用交换或修改整体提交，悬空条件组不得进入存储 |
| 装备替换：角色协调资产 | 角色和装备归属、占用、职业、主槽/阻塞槽、承载；卸旧/穿新及位置关系一起变化，不复制装备实例 |
| 转职：角色协调资产 | 来源职业/资格/占用/版本；更新职业并卸回全部装备，保持身份、成长与已学技能规则一致 |
| 精炼/制作：资产 | 位置/归属/占用、配方/材料/费用；消耗与实际随机结果一起提交，失败不出现无材料产物。正常精炼结果按旧规则处理，不能把游戏失败当成事务错误免成本 |
| 战斗结算：对应玩法 | 上述受理、演算、结算协议；成长、资源、共享玩法结果及结算凭据不可拆开 |
| 商店购买/出售、打工：交易协调资产 | 当前交易条件、可用钱/物/体力及库存如适用；钱物增减或体力→钱交换一次提交，不能超卖/多扣 |
| 上架/竞价/到期：交易协调资产 | 标的唯一位置、状态/版本、出价规则、到期时刻；上架费与标的占用，或新出价款、旧出价退款与报价状态，或卖家款、买家物与结算终态，各自在自己的单次事务中完成 |
| 角色/账号删除：对应所有者协调相关模块 | 必须检查未结操作、占用、交易债权债务及被引用状态；账号失效、会话撤销、角色/资产/编队与玩法引用清理不得分步对外生效。不能靠数据库级联删除其他玩家的应收资产；未结交易如何处理归账号/交易专题，未明确前不能实现强制跳过 |
| 管理修正：运营协调所有者 | 权限、修正目标版本、理由和占用；通过同样的业务操作完成修正与记录，不能绕开有效战斗或结算凭据 |

跨账号拍卖结算在同一个 SQLite 事务内修改所有受影响账号，不为每个账号分别提交。结算过程中最新余额可能已变化，退款和收入均为增量操作。正式拍卖扣款/资金占用、结束时间与删除规则由交易专题精确定义，不把本表当作已批准改变拍卖玩法。

## 验收与后续归属

| 确定性场景 | 必须成立的结果 |
| --- | --- |
| 余额只够一次，两笔不同购买并发 | 至多一笔成功，余额不负，成功项钱物齐全；相同请求重试仅返回同一笔 |
| 两个请求争用同一装备 | 只出现一个合法位置/占用，不能穿戴后又卖出或上架 |
| 手机已改战术，旧电脑页面提交 | 拒绝旧版本，保留电脑编辑内容，服务器新配置不变 |
| 战斗中改出战角色/装备，同时改候补或收到拍卖款 | 冲突修改被拒绝；不冲突操作保留；战斗结算不覆盖新收入 |
| 多次领取同一战斗收益，含新请求标识 | 同一业务来源仅生效一次，成长、钱物、流水和终态一致 |
| 受理后/演算中/提交前后注入进程中止 | 按故障表恢复或取消，无额外随机结果、重复收费、发奖或永久残留占用 |
| 恢复执行者已领取，旧执行者迟到；取消与提交同时发生 | 当前执行代次和终态检查保证只有一个可生效结果 |
| 拍卖到期重复运行、卖家/买家同时消费 | 只结算一次，双方增量余额和物品归属正确，不覆盖其他交易 |
| 体力达到上限后预留/恢复/取消，含小数余额 | 预留不被二次花费，释放不覆盖期间变化，不丢精度或额外产生恢复额度 |
| 删除仍有在途战斗或对外义务的账号 | 不留下可提交的旧执行者或无归属交易资产，不误删他人权益 |
| 流水或战报写入失败 | 对应业务变更不能单独提交；响应丢失后可查已提交结果 |
