# 角色、职业、技能与装备内容模型

状态：用户已确认 Q1–Q4。对应 [确定角色、职业、技能与装备的内容模型](https://github.com/odradekk/hof_redux/issues/4)。以下记录已确认的模型及其工程约束；文末明确分配给后续议题的细节尚未裁定。

前置：[玩法保真基准与差异裁决登记](../legacy/fidelity-decisions.md)。本议题确定领域关系、定义与实例、引用和约束，不确定数据库表结构、接口协议或完整战斗公式。

## 已确认

- Q1：一次获得经验允许连续升级。逐级扣除经验需求、发放该级属性点和技能点；非满级时剩余经验保留。成长在旧版对应的战斗过程时机发生。
- Q2：装备从获得时起逐件拥有独立身份；精炼、装备和出售指向具体装备。相同装备可在界面合并显示、批量操作；材料等无个体差异的物品按数量堆叠。
- Q3：达到等级上限时剩余经验归零，满级后不再获得经验。这是溢出经验保留规则的明确例外，不建立满级经验储备。
- Q4：确认角色成长状态与战斗临时状态分开；职业与转职关系分开；技能学习规则数据化；装备定义与逐件状态分开并保留效果顺序；配方独立；怪物复用战斗描述而不套用玩家成长/归属状态。

## 模型与关系

| 概念 | 定义或持久状态 | 关系与约束 |
| --- | --- | --- |
| 账号 | 账号身份；其拥有的角色与资产 | 角色归属一个账号；账号与角色身份分开，登录和删除契约归账号议题 |
| 招募模板 | 初始职业、基础属性、初始技能/装备、价格及展示选择 | 引用职业与物品定义；四个旧招募模板不是四种角色实例或四个独立职业系统 |
| 角色 | 独立身份、名称/性别、创建时刻、当前职业、等级/剩余经验、基础五维、未分配属性点/技能点、已学技能、位置/保护策略、战术方案 | 可学技能、HP/SP 上限等由规则推导；不把战斗中的受伤、异常状态或施法进度作为角色常驻成长状态 |
| 编队 | 有序角色引用 | 引用本账号角色、成员不重复，当前普通出战为 1–5 人；记忆队伍与竞技防守用途分开，防守快照语义归竞技议题；首期不额外增加多套队伍预设 |
| 职业 | 稳定身份、名称/外观、成长系数、装备适用关系 | 转职为独立的来源→目标关系；不靠编号前缀推断职业族，也不写死最高转职次数 |
| 转职关系 | 来源职业、目标职业、资格条件 | 旧版按职业候选与等级门槛表达；转职保留等级、经验、基础属性、点数及已学技能，重新计算职业相关值，并将装备全部卸回背包 |
| 技能定义 | 名称/图标、主动使用与被动效果描述、资源/时序与效果定义 | 技能学习资格与战斗使用规则分开；不预设主动与被动效果必须互斥；普通效果按明确类型与参数表达，特殊效果引用具名处理器；效果执行语义由战斗议题确定 |
| 技能学习规则 | 目标技能、适用职业/职业集合、前置技能和等级条件、学习成本 | 已学技能是角色状态，可学集合是计算结果；以 all/any 和有限类型的条件表达旧规则，不在 JSON 中执行脚本 |
| 战术方案 | 一个当前方案与一个备用方案；各自保存有序条件、参数、技能规则行 | 切换交换二者，备用不是未保存草稿；旧初始数据可未配置备用方案，模型明确表达未配置状态，不新增任意多套方案。执行与未配置时的缺省动作归战斗议题；行数上限按旧基础 INT 和等级计算 |
| 保护策略 | 必定、不保护、HP 比例条件或概率条件 | 使用明确类型与参数，不把旧拼写字符串作为规则；条件运算符、概率边界及修复见下方待决项 |
| 物品定义 | 稳定身份、名称/图标、分类、价格、用途和适用规则 | 装备、材料及特殊用途道具明确区分；不假定所有非装备都是可在战斗中使用的消耗品 |
| 装备定义 | 物品的装备分类、占槽关系、承载消耗、基础数值与精炼规则引用 | 当前武器/盾/甲/道具四槽；双手武器占用关系与职业许可分别验证，不依赖中文名称判断类型 |
| 持有装备 | 独立身份、定义引用、所属账号、所在位置、精炼等级、有序附加效果及来源 | 一件装备只能位于一个合法位置，不能同时装备给两个角色、留在背包又上架；交易占用和原子变更契约归事务/交易议题 |
| 堆叠物品 | 所属账号、定义引用、数量 | 同一堆叠的单位可互换；数量不得为负，具体整数范围在存储/内容校验时明确 |
| 附加效果 | 稳定身份、类型化效果和参数 | 旧制作有追加材料、随机高阶、随机低阶三个来源，持有装备记录实际抽取结果及顺序，不能只记录“以后再抽”的效果池 |
| 制作配方 | 材料与数量、输出定义、费用、可用追加材料和效果池引用 | 当前制作费为零；配方独立于装备定义，新增已有机制的配方只补数据；保留随机分布与抽样顺序 |
| 怪物定义 | 等级、基础属性、HP/SP、攻防、技能/战术、位置/保护、经验/金钱奖励、掉落与特殊机制引用 | 与角色共享战斗所需描述，不强行赋予账号、经验条、招募或玩家装备归属；奖励定义留在怪物/遭遇内容侧，遭遇生成与战斗实例分开 |

## 字段含义与引用契约

以下是领域字段约定，不是数据库 DDL 或 HTTP 数据结构。名称可在实现时按统一编码约定调整，含义与约束不能静默改变。

| 记录 | 关键字段 | 含义 |
| --- | --- | --- |
| 招募模板 | `id, jobId, initialStats, initialSkillIds, initialEquipment, price, presentation` | 一种可购买的初始角色配置；价格使用旧值，创建角色时产生新角色/装备身份 |
| 角色 | `id, accountId, name, gender, createdAt, jobId, level, experience, baseStats, attributePoints, skillPoints, learnedSkillIds` | `experience` 是当前等级内尚未消耗的经验，不是累计经验；`baseStats` 明确为 STR/INT/DEX/SPD/LUK；已学技能不重复 |
| 角色配置 | `equipmentSlots, position, guardPolicy, activeTactics, backupTactics` | 装备槽引用持有装备 ID；前后排和保护设置属于角色配置，战斗中变化另存；战术主/备各存完整有序行或未配置状态，切换交换两者。增删操作针对方案中的规则行，不是增删任意数量的方案 |
| 编队选择 | `characterIds` | 有序且不重复的角色 ID；候补角色仍属于账号，未选中不等于删除 |
| 职业 | `id, presentation, hpSpCoefficients, allowedEquipmentTypeIds` | 展示可按旧性别配置变化；装备种类是稳定分类引用；旧成长系数分别作用于 HP/SP |
| 转职关系 | `id, fromJobId, toJobId, requirements` | 有向关系与资格条件；添加更深层职业无需修改转职流程代码；不会自动赋予回转、降阶或自由换职能力 |
| 技能学习规则 | `id, skillId, requirements, skillPointCost` | 资格包括显式职业集合、已学技能和等级条件；多个条件用 all/any 组合；旧技能成本一致，不擅自引入职业差价 |
| 战术规则行 | `conditionId, parameters, skillId` | 引用条件定义与技能定义；条件参数是声明过单位和类型的值，不能提交任意表达式；优先级由数组顺序表达 |
| 装备定义 | `id, equipmentTypeId, primarySlot, blockedSlots, effectCategoryId, handleCost, baseValues, refinementRuleId` | 装备在主槽引用，其他槽仅被阻塞；双手武器不生成第二件实例或第二份装备加成。职业许可类型、占槽、附加效果适用分类分别表达，不互相推导；武器物攻/魔攻、防具物理/魔法减免字段各有明确定义 |
| 持有装备 | `id, itemDefinitionId, accountId, location, refinementLevel, affixes` | `location` 表达唯一合法位置；`affixes` 是有序条目，每条包含 `effectId` 和来源（追加材料/高阶/低阶），保留空缺与次序语义 |
| 堆叠物品 | `accountId, itemDefinitionId, quantity` | 只用于无个体差异的物品；零数量可从持有列表中移除，负数量非法 |
| 制作配方 | `id, ingredients, outputItemId, moneyCost, additionalMaterialRules, affixGenerationRuleId` | 材料条目为定义引用和数量；当前费用为零；随机规则引用确定的内容池与代码机制，结果写入持有装备，不在查看物品时重新抽取 |
| 条件/效果定义 | `id, kind, parameters` 或 `id, handlerId, parameters` | `kind` 是系统已实现的明确规则类型；特殊机制引用已登记处理器。每类参数独立校验，未知类型/字段/处理器不默默忽略 |
| 怪物定义 | `id, level, baseStats, maxHp, maxSp, attack, defense, skillIds, tactics, position, guardPolicy, experienceReward, moneyReward, drops, mechanics` | 为遭遇生成战斗单位提供输入；经验、钱与物品奖励分别定义，结算时机与分配归战斗/冒险议题；召唤、时段变化、世界 Boss 等特殊机制通过明确引用继续建模，不把动态 PHP 表达式塞入 JSON |

内容的发布版本、具体 ID 命名、效果类型全集与序列化 schema 由内容发布/战斗议题完成。这里给出扩展位置，未承诺用一个通用效果类型覆盖全部旧技能。

## 身份、状态与扩展约束

- 内容 ID 是不随显示名称变化的字符串引用。旧编号另留来源对应关系；从 ID 不推导等级、职业族、物品类型或精炼。具体命名与文件组织由内容发布议题统一。
- 角色和装备的运行期 ID 与内容 ID 属于不同概念。改名不改变身份；精炼不更换装备身份；出售转移的是持有装备，而不是修改装备定义。
- 定义与玩家状态分开。数值面板由基础值、职业、装备和被动技能计算；战斗快照再保存本场临时 HP/SP、异常状态、行动位置与施法状态。世界 Boss 的共享 HP/SP 是该系统的特殊持久状态，不套用普通角色规则。
- 条件与效果使用可校验的明确类型，不建立通用任意属性字典。新增已有机制的职业、技能、装备或怪物可只补定义和引用；新增机制时添加集中处理代码及参数校验。
- 附加效果保留来源和应用顺序。旧版先精炼再按追加材料、高阶、低阶顺序应用效果；不要为了归一化而排序、去重或合并效果，除非已证明数值与行为等价。
- 同状态装备的界面分组不改变逐件身份。已核对旧物品定义中的配方材料引用，共 18 种，全部属于材料；当前配方不需要消耗持有装备。不为未来可能的“装备作材料”预建选择机制。上架和批量出售的具体装备选择归交易契约。
- 首期继续采用旧转职、技能、装备和队伍内容；模型能表达未来新关系不等于本次增加三转、镶嵌或新技能内容。

## 必须保持的不变量

1. 内容引用必须存在且类别正确；角色 ID 不能充当职业 ID，装备实例 ID 不能充当物品定义 ID。定义引用唯一、可追踪到旧来源；不可达定义保留并标记不开放，不因校验成功自动向玩家开放。
2. 角色归属与出战归属一致，队伍成员不重复；删除角色后的引用清理由角色/账号操作保证，不能依靠页面隐藏残留引用。
3. 成长点数、等级与经验使用同一次成长结果更新。非满级时，连续升级结束后满足 `0 ≤ experience < 当前等级升级需求`；满级时 `experience = 0`。按实际经过的等级应用旧经验需求和对应收益，不能把不同等级的需求当作固定值。
4. 当前职业与转职来源匹配且满足全部门槛，才能转职。已学技能保留不等于能绕过新职业的学习门槛；是否可在战斗中使用还要符合该技能本身的使用约束。
5. 学习技能时，对实际传入的同一个技能验证内容存在、学习资格、尚未学习及点数充足；成功一次扣点并学习，失败不留下部分变更。领域校验不读取 HTTP 全局变量。
6. 战术保存须验证条件、参数及动作引用；主/备方案遵循同一内容合法性规则，切换不能丢失原当前方案。允许的行数按旧规则计算，不能靠任意新增数组元素绕过上限。条件参数区间、重置属性后行数变少和未配置方案的处理由战斗/角色规则继续核对，不能静默截断玩家方案。
7. 装备所处位置、槽位引用与账号归属一致。同一件装备不能被两个角色占用或同时处于背包和交易占用状态；职业许可、占槽冲突和总承载上限都必须满足。装备替换与转职卸装保留装备身份和效果。
8. 配方只消耗其声明的材料和追加材料，结果及费用一次结算；当前材料不足时不能生成产物。内容抽取必须核对随机高/低阶效果的组合分布及抽样次数，不能换成“每个效果独立随机”而改变分布。
9. 角色存档、派生面板与战斗状态各有职责。计算缓存即使存在也不是第二份规则来源；成长产生的持久变更由战斗结果明确携带，不能整对象保存临时异常状态。

事务落地、版本冲突与幂等细节归[事务边界](https://github.com/odradekk/hof_redux/issues/6)；这些不变量是其输入，不在本议题选数据库写法。

## 后续议题的明确输入

- 已确认的[战斗契约](combat-contract.md)规定机制族、派生值更新时机、数值顺序、条件参数边界与修复行为；逐内容字段映射和发布校验继续归内容发布议题。
