## 交付结果与范围

用户在 Linux 上运行固定版本的 Docker 部署，通过网页注册账号、保存恢复码、登录并完成首次建队，招募战士/法师，选择 1–5 名角色前往 gb0，得到真实成长和掉落，查看公开静态战报；退出、刷新或重启后仍能核对已保存结果。需要人工介入的故障可从独立管理后台诊断和处理。

S1 是受控测试版本，进度不承诺继承，重置仍须先说明并遵守授权。远程试用使用 HTTPS，公开战报的游戏内权限与测试环境的访问控制分别处理。服务器、域名、测试者访问方式和告警 Webhook 在实际 Linux 环境准备时落实，不预设已有资源，也不因本文确认自动购买或部署。

## Linux 与 Docker 工作方式

采用已确认的 Compose 单机方向，开发与阶段验收使用同一套工程和部署基础。开发模式允许源码挂载与热更新；验收模式构建固定应用/内容/素材版本的镜像，避免试用结果随未提交源码变化。[Docker 的多环境 Compose 指引](https://docs.docker.com/compose/how-tos/production/)

开发、自动测试、人工试用和恢复演练分别使用独立数据库路径、配置、凭据与备份目标；可在条件允许时使用同一 Linux 主机上的不同实例，不要求本轮采购第二台服务器。Compose 项目名可区分运行实例，但宿主持久路径和对外端口也必须明确隔离，不能仅换项目名却仍挂载同一数据库。[Compose 应用模型](https://docs.docker.com/compose/intro/compose-application-model/)

- Caddy 提供前端静态产物和 API 同域入口，后端在内部网络运行；SQLite 是后端使用的本机持久文件，不增加数据库服务容器。数据库和备份不能只存在于容器可写层。
- Node 24、内置 SQLite、WAL/FULL、单业务连接与受控战斗线程池按[运行契约](runtime.md)落实。具体补丁版本、镜像摘要、依赖及命令在 Linux 实施时核验锁定，不将当前规划机器上的版本当作交付版本。
- 一般启动或重建容器不重置数据库、账号、操作身份或随机状态。测试数据初始化只针对明确隔离的测试实例；不能在每次应用启动时自动补钱、清占用或重建角色。
- 提供可重复执行的构建、启动、检查、停止、备份及隔离恢复步骤，失败须明确报告，不用一条脚本掩盖其中尚未完成的恢复步骤。
- 基本维护和版本切换遵守暂停受理、处理在途操作及兼容性检查；无法安全完成则保留原状态，不为切换版本强行取消战斗。S1 的本地一致备份验证不冒充 S2 的异机备份，也不声称完整生产发布/灾难恢复门槛已经通过。

## 事务、恢复与最小后台

S1 沿用[状态与事务](state-transactions.md)、[接口](interface-contract.md)和[账号](accounts.md)契约。注册、首次建队、招募和战斗的资产/成长及操作结果在各自业务事务中一致提交；跨模块通过所属模块操作协作，不由 HTTP 层分别扣款、建角色和写背包。

战斗受理前取得处理名额，在短事务内固定角色/敌队、规则版本、随机状态、体力预留和占用；工作线程只计算固定输入，不访问数据库。成功结算和故障取消争用同一终态；结果未知时先查询，失去执行权的旧线程不能提交。未受理时不保存记忆队伍，已受理后的故障取消不回滚已保存记忆。

临时故障按既定 5/15/30 秒进行三次额外重试，次数持久保存；重试耗尽或受理满 5 分钟未完成须告警并保留记录/占用。确定性错误以原版本、原输入和原随机状态复核，满足契约条件才自动取消。不能因普通断线、进程崩溃、超时或暂时缺少版本文件直接取消或重新抽取结果。

| 管理入口 | 最小行为与限制 |
| --- | --- |
| 独立登录 | 密码登录、既定会话期限及近期验证；玩家身份不能进入。服务器管理者通过受控命令创建/撤销管理员或重置其密码，动作留记录，撤销/重置使旧管理会话失效；不提供默认共享账号或公开注册管理员 |
| 操作列表/详情 | 查待处理战斗、处理阶段、故障类别、重试状态、必要版本/身份引用和占用；核对原终态，不公开凭据或完整内部输入 |
| 恢复原操作 | 校验原记录、当前执行权和业务条件，恢复同一场；已完成返回原状态，不创建新的随机结果 |
| 故障取消 | 只有符合已批准取消条件才可执行，预览对象和资源影响、填写原因、近期密码验证；一次释放预留和占用，不计胜负/收益，重复执行不重复释放 |
| 审计与通知 | 修改和记录一同提交，审计可查询不可逐条改删；故障通知含摘要/排查编号，实际验证 Webhook 送达，不发送凭据、IP 或完整输入 |

后台能显示“尚不满足取消条件”，不提供任意取消或直接编辑数据库按钮。完整资产修正、停用/删号、统计、社区管理和批量清理仍按后续阶段交付。操作页面失效或数据库故障时，不能用未鉴权接口绕过；服务器管理者的恢复步骤另有记录。

每次记录应用提交、内容/素材/数据库版本、镜像、设备/浏览器、测试入口、预期、实际结果和证据位置。用户完成主要玩家流程和故障管理试用后确认 S1；未执行的项目不写成通过。S1 先积累真实请求与战斗耗时，不以少量测试宣称 100 人承载或最终性能达标；完整硬件、历史库、时限和长时负载仍受[验收契约](acceptance.md)约束。

## 待实施核验与本轮边界

具体依赖补丁和镜像、JSON Schema 字段、数据表/索引、HTTP 路径、查询分页、战报检查点、线程/名额/执行预算及认证限流等由 AI 在 Linux 实施中选定、验证和记录，遵守已有契约。不能让用户凭空决定性能常量，也不能把未知数留到交付后；S1 可执行内容需要相应预算和输入限制，后续增加机制时重新验证。

Linux 主机资源与地址、HTTPS 条件、受控访问方式、Webhook 目标和凭据提供属于环境准备任务；秘密不放入规格或仓库。缺少时可以继续独立实现与隔离测试，但相关交付项保持未完成，不假定告警或手机访问已经验证。

当前 `old_hof/` 未纳入 Git，Linux 上仅克隆托管仓库不会取得旧源码和素材。环境交接须准备只读白名单参考文件及来源摘要，包含所需代码、内容定义、素材和已筛选的玩法常量；不整体复制旧运行目录，不携带玩家样本、凭据或日志，也不将旧实现装入生产镜像。引用依赖核验完成前，不能仅凭规划中的编号表伪造完整提取结果。

本轮最终确认只完成 S1 规格及文档纠正；后续先审阅开发任务拆分，再进入实施，不重开已完成的整张 Wayfinder 地图。若取证发现新的玩法矛盾，明确记录并裁决，不能以常规技术选择名义静默改规则。
