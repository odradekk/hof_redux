# HOF Redux：完整重写的架构与实施计划

## 1. 已确认边界与本计划的性质

已确认的产品方向：

- 以 PHP 8.4.26 为目标运行环境，全面重写，不以修补旧程序为主线
- 首次对外发布就是功能完整版本；允许内部按阶段验收，不把内部阶段当作对外缩水版本
- 没有需要保留的现有玩家；不迁移旧账号、角色、背包、拍卖、排行榜、战报或共享 Boss 运行状态
- 复用旧界面布局与静态素材；不等于保留旧 PHP 模板、入口参数、数据库格式或不安全交互
- `hof_redux` 的 `c3920ac` 作为只读规则、内容与素材参考，不进入生产镜像，也不执行旧站导出数据

用户已授权按此计划开始完整重构并同步上游。技术栈采用 Laravel 13、Blade、PostgreSQL 18、PHP 8.4.26-FPM、Nginx 和 Docker Compose；目标 Linux 服务器。拍卖和打工完整恢复，技能重置补齐。模块划分保持 KISS，可在实现中合并不必要的层次；部署规模仍待实测。本文不以“文件存在”替代功能确认，完整范围以单独的功能追踪清单为准。

## 3. 总体结构：单库、模块化单体、服务端渲染

建议一个应用、一个支持事务的关系型数据库、一份可独立部署的构建产物。Web 请求和定时维护命令使用同一套应用服务。初版不拆微服务，不引入消息中间件，不把事件日志当成唯一事实来源，也不为每个类创建接口。

建议目录：

- `src/Identity`：账号、安全与访问权限
- `src/Player`：玩家档案、角色成长、阵容与行动配置
- `src/Economy`：货币、背包、装备位置与资产流水
- `src/Activities`：狩猎、工作、商店、招募、锻造等应用流程
- `src/Auction`：拍卖规则、竞价与结算
- `src/Competition`：排行榜与挑战流程
- `src/WorldBoss`：共享 Boss 生命周期及挑战流程
- `src/Combat`：纯战斗模型、行动判定、效果与事件
- `src/Content`：经验证的静态内容和查询
- `src/Community`：已确认的留言、公告等功能
- `src/Web`：路由、控制器、请求验证、页面数据组装
- `src/Infrastructure`：数据库实现、事务管理、会话、日志、任务运行
- `templates`、`assets`、`content`、`tests`、`migrations`

这些是命名空间与职责边界，不要求每个模块复制一整套空的 Domain/Application/Infrastructure 子目录。模块内部先使用清晰的具体类，只有跨模块入口、随机源、时钟和确实需要替换的基础设施才建立小型稳定契约。

### 状态所有权与公开入口

| 模块 | 唯一拥有的可变状态 | 典型命令 / 查询 |
| --- | --- | --- |
| Identity | 账号凭据、会话、安全状态、管理权限 | RegisterAccount、Authenticate、ChangePassword / CurrentIdentity |
| Player | 玩家显示资料、角色基础属性/成长/经验/职业/技能、行动条件与阵容；行动资源和冷却 | RecruitCharacter、ChangeJob、LearnSkill、SetParty、SetTactics、ConsumeActionBudget / Roster、BattleSnapshot、Eligibility |
| Economy | 货币可用额和托管额、资产流水、道具数量或实例、道具位置（背包/装备/拍卖托管）、装备栏分配 | Debit、Credit、ReserveFunds、ReleaseFunds、TransferReservedFunds、MoveItem、EquipItem / Balance、Inventory、EquipmentLoadout |
| Activities | 活动专属的必要状态；绝不另存一套货币或物品 | Hunt、Work、Buy、Sell、Craft、Refine、Recruit、Equip / ActivityOptions、Quote |
| Auction | 拍卖条目、竞价历史、最高价者、结束时间、状态与结算标记 | ListItem、PlaceBid、SettleAuction / AuctionList、AuctionDetail |
| Competition | 榜单位置、挑战记录、已登记阵容引用或快照的版本 | RegisterRankParty、ChallengeRank / Ranking、ChallengeHistory |
| WorldBoss | Boss 实例、HP/状态、生成与复活期限、挑战及贡献记录 | ChallengeBoss、RespawnBoss / ActiveBosses、BossStatus |
| Combat | 一次模拟的内存状态；不拥有持久玩家状态 | Simulate / 返回 BattleOutcome 和结构化事件 |
| Content | 不可变、带版本的内容包 | Item、Skill、Job、Monster、Recipe、Area、JudgeDefinition |
| Community | 留言、公告及审核状态 | PostMessage、ModerateMessage / Board、Notices |

补充约束：

1. `Economy` 拥有装备位置，`Player` 不复制存储物品编号到第二套装备栏。最终战斗快照由应用层组合角色属性、装备和内容。
2. `Player` 中行动资源/冷却的记录可按活动键区分，但统一校验和提交；活动模块负责解释本活动规则，不能各自绕过资源扣减。
3. 全部持久资产变更留下原因、操作 ID 和关联对象。流水用于审计与对账，不要求全量事件溯源或财务级复式账系统。
4. 招募、装备等跨边界流程由 Activities 的具体用例编排，不让底层模块互相回调。
5. 战报由独立存储适配器保存模拟输入摘要、版本、种子与事件；各玩法只引用 battle ID。无需为了这一点单独建复杂业务模块。

### 允许的依赖方向

- Web → 各应用用例 / 只读页面查询
- Activities、Auction、Competition、WorldBoss → Player、Economy 的公开能力，Content 与 Combat
- Player → Content；Economy → Content；两者互不直接依赖
- Combat → 自己的值对象和已解析内容契约；不得依赖 Player 实体、数据库、Web 或全局配置
- Community → 身份 ID 与授权上下文，不读取凭据
- Identity 不依赖游戏模块
- Infrastructure 实现存储和运行支撑；由启动层装配到应用，不把容器散布进业务对象

禁止跨模块直接写表、访问其他模块内部仓库或传递“万能 User 对象”。报表型跨模块读取由明确的查询类完成，只返回页面 DTO，不经由读取接口偷改业务状态。可以用静态依赖检查阻止逆向引用，不先自建插件系统或通用命令总线。

## 4. 事务与并发：先定义不变量，再写流程

### 全局不变量

- 货币、可用物品、托管物品都不为负；数值使用有范围检查的整数
- 同一个道具实例只能在一个合法位置；可堆叠数量在转移前后守恒，消耗与产出有明确原因
- 一个操作只结算一次；重复提交、刷新、超时后重试都不能重复扣费或领奖
- 每个拍卖只有一个最终结果，每个 Boss 实例只能发生一次最终击杀状态转移
- 客户端只传意图、目标 ID、选择项与幂等标识；价格、所有权、技能可用性、冷却和奖励由服务器重新计算

### 原子用例

| 用例 | 同一事务必须包含 |
| --- | --- |
| 购买/出售 | 身份与资格校验、锁定资产、服务器定价、扣钱/加钱、物品增减、流水、操作结果 |
| 锻造/精炼 | 配方/材料/装备版本校验、所有成本消耗、成功或失败结果、物品变化、流水；业务失败也按规则形成唯一结果 |
| 装备替换 | 背包和全部受影响装备栏移动、双手/盾牌和负重校验；任何校验失败则整体不变 |
| 招募/成长 | 费用或点数扣减、上限/前置条件校验、角色/职业/技能变更及操作结果 |
| 拍卖上架 | 费用、物品托管、拍卖创建；禁止先扣上架费再验证物品 |
| 拍卖竞价 | 条目锁定、重新检查结束时间和资格、锁定相关账户、新竞价托管、旧竞价退款、最高价/延时更新、流水 |
| 拍卖到期 | 条目终态校验、唯一结算、物品转移、卖方收款或流拍返还、托管清零、流水 |
| 狩猎 | 资源/冷却、角色结算、奖励货币与物品、战斗结果索引和幂等结果 |
| 排名挑战 | 排名/双方阵容版本验证、挑战冷却、明确规定的双方变更、名次调整、唯一挑战结果 |
| 共享 Boss | Boss 最新状态、挑战资源/冷却、实际伤害和存活状态、贡献/奖励、角色结算、唯一结果 |

一次应用用例只由一个最外层事务负责人开启和提交。模块仓库共享同一连接和事务上下文，不能每调用一个模块就各自提交。任何异常都回滚资产与业务状态；页面成功提示只能在提交之后产生。

### 幂等、锁与故障

- 每次可重复的写操作使用 `(actor_id, command_type, operation_id)` 唯一键，并绑定请求参数摘要；相同键不同参数拒绝，相同请求返回原结果
- 约定全局锁顺序，例如玩法对象 → 玩家按 ID 升序 → 资产按固定顺序；所有路径遵守同一规则
- 数据库约束防重复、负库存和无效引用；应用校验提供可理解错误，两者都需要
- 死锁等可恢复事务错误允许有界重试；重试复用操作 ID、规则版本和服务端随机种子，避免用户重试获得不同结果
- 事务外不可先发奖励、输出不可撤销结果或写唯一外部战报；首版可将必要战报数据同事务存库，外部文件仅作为可再生成副本
- 定时结算与 Web 到期触发调用同一个 `SettleAuction`，依靠锁和终态约束防止重复执行；后台任务不可成为唯一正确性来源

### 战斗计算与事务长度

建议先实现最易验证的同步方案：锁住受影响状态，在严格回合/行动上限内运行纯内存模拟，原子结算并保存结果；事务内不渲染 HTML、不访问网络、不写文件。用真实复杂度的测试测出事务时长和锁等待，不在未知性能情况下承诺可承载规模。

若基准测试表明同一 Boss 或排行榜的锁等待超过批准的性能预算，再调整为“版本化快照 → 锁外计算 → 短事务校验版本并结算”。版本冲突必须用新快照重算或明确要求重新挑战，不能把针对旧 HP 的伤害机械叠加到新 Boss；重试耗尽不扣资源、不落奖励。该优化不是首版默认引入的队列/工作流系统。

排行榜需要按实际排名结构锁定足够范围。首版允许用一个榜单版本/互斥记录串行化排名变化，先保证相邻位置和同名次容量正确，再由压力测试决定是否细化锁。

## 5. 纯战斗核心

### 输入与输出

输入为完整快照：双方角色/怪物、已解析装备加成、行动规则、技能与条件内容、战斗模式、规则版本、内容版本、显式随机状态。输出为最终内存状态、结果、结构化事件与候选结算数据。结算应用服务决定哪些变化允许持久化：模拟战、排名战、普通狩猎、Boss 战不能共用一个无条件的“保存所有角色”。

核心不读取 `$_GET`、`$_POST`、`$_SESSION`，不调用 `time()`、全局随机函数、文件或数据库，不打印 HTML，不靠继承用户持久实体获得战斗能力。

### 随机、时间与可重放

- 使用很小的显式随机源契约，测试可传入固定序列；服务端产生并保存种子，玩家不能自选种子
- 每次战斗使用局部随机状态；禁止污染整个进程的全局随机数发生器
- 保存随机算法版本，规定相同输入、规则版本、内容版本和随机状态得到相同的事件与结果
- 战斗内时间使用离散 tick/延迟值；行动并列、延迟重算、蓄力/吟唱、硬直及追加回合的顺序必须写成规则
- 墙钟时间只出现在应用层，用可替换 Clock 读取；一次事务中的资格校验使用明确的一次时间快照，并在取得关键锁后判断期限
- 保存规则构建标识及相应可部署产物；仅有 seed 但规则代码已变，不等于可重算旧战斗。首版至少保证旧事件可原样回放，跨版本重算需保留对应构建

### 结构化事件

例如 `BattleStarted`、`ActorSelected`、`SkillUsed`、`TargetSelected`、`DamageApplied`、`StatusChanged`、`Summoned`、`ActorDied`、`BattleFinished`。包含稳定单位 ID、事件序号、tick、数值与规则原因，不包含拼好的 HTML。

显示层将事件翻译成原有风格的文字、颜色、图标、位置和隐藏信息；Boss 的隐藏 HP 应在输出视图做过滤，不能把真实值发送给前端再用 CSS 隐藏。日志详细度可控制，但计算与展示不能形成不同的结果来源。

### 有限且明确的效果系统

普通效果用少量有类型的结构表示：伤害、治疗、状态、属性变化、位移、延迟、召唤、资源变化。特殊技能用具名处理器注册，例如源码里 ManaBreak、SoulBreak、LifeDivision 等有独特步骤的技能；不要为了消除所有特殊代码先开发可执行 DSL。

行动条件同样使用有限枚举和经过验证的参数。未知条件、未知效果或缺失处理器在构建时失败，不能运行时静默变成普通攻击。每个特殊处理器至少有正常、边界和不合法目标测试。

## 6. 内容：提取、归一化、校验、发布

内容包与玩家运行数据完全分开。建议优先使用简单、无可执行逻辑的 JSON 加明确 schema，按类别拆分；最终格式不构成用户已批准的选型。

1. 按白名单读取旧源码与静态素材，记录来源文件、位置、旧 ID 和源文件指纹；不 `include` 旧 PHP，不执行旧入口
2. 对常量表达式、条件定义、动态生成字段和特殊技能分别建提取清单；无法安全静态提取的项人工核对，不能猜默认值
3. 保留旧内容 ID 作为可追踪业务标识，但新数据库主键、账户 ID、存档格式无需兼容
4. 校验字段类型、整数范围、概率/权重、技能目标组合、配方引用、职业前置、怪物技能、召唤引用、地区掉落、图片路径与素材存在性
5. 检查引用图中的非法环、自引用和不可达内容；合法的互相克制等关系不得误判为错误
6. 每条内容与每种有效效果都有“已提取 / 已实现 / 已验证 / 明确排除”的状态；未实现效果不能混在可发布内容里
7. 归一化统一编码和数值，但保留来源与批准差异；规则修正另写行为差异清单
8. 构建生成不可变 `content_version`；一次运行/战斗引用确定版本，禁止后台直接编辑已发布内容造成半新半旧

旧错误分三类：安全/数据一致性问题直接按新版标准消除并记录；明确死代码排除且保留依据；会改变玩家感受或数值平衡的歧义提交产品决策。不是所有旧 bug 都值得精确复刻，也不能借“重写”擅自改玩法。

## 7. Web 与旧视觉的隔离

- 默认服务端渲染，保留原有页面分区、菜单顺序、战报布局、图标和主题；不默认改成 SPA
- 控制器只负责输入验证、登录/权限、调用一个用例、选择模板；模板只读取明确页面数据
- 所有写操作使用受保护的 POST，带 CSRF 防护与服务端权限检查；不保留 GET 扣费/战斗等副作用
- POST 成功后跳转，重复提交仍由后端幂等保护；前端禁用按钮只是体验优化
- 输出转义、白名单资源路径、安全会话、密码哈希、登录限流、管理审计纳入基线
- 用户名称、留言、拍卖说明和战报中的名字都按不可信文本处理；不沿用可执行的旧 HTML 拼接
- 复用 CSS 时逐页提取，命名冲突在模板边界解决；需要修正的无效 HTML 或失效交互不属于视觉背离
- 桌面忠实还原，同时保证窄屏可阅读和操作；不以“复古”为由接受不可点击按钮、错位表单或泄漏信息

先为登录、主城、角色、背包、狩猎、战报、商店、锻造、拍卖、排行、Boss 和管理页面确定参考截图或人工界面清单。旧站不能安全运行时，用静态模板与素材取证建立批准的视觉基线，不假称已经对旧站做截图回归。

前端视觉语言、组件、逐页方案与静态视觉基线原型见 [frontend-redesign.md](frontend-redesign.md)。

## 9. 测试策略与发布门槛

### 规则测试

- 固定输入/固定随机序列的伤害、命中、目标选择、状态、延迟、召唤、阵型和胜负测试
- 同行动顺序的稳定性，SP 不足、无合法目标、全员死亡、平局、回合延长上限、溢出与除零边界
- 角色基础状态与战斗状态分开，战后哪些状态保留按模式逐项断言
- 属性测试/随机组合测试：不出现非法 HP/SP、无限行动、无所有者单位或无效目标引用
- 旧源码只作为取证依据；没有可安全运行的旧环境就不宣称实现了差分测试。可建立经人工核对的规则样例作为黄金数据

### 数据库与并发测试

使用实际选定的生产数据库引擎和多条连接，而不是仅用内存替代品证明锁正确。

- 两次购买争用同一余额；最后一份物品同时出售和装备
- 两人同时竞价；新竞价与拍卖到期同时发生；原竞价退款后立刻花钱
- 结算重复调用；提交成功但客户端超时；事务任意关键点异常
- 两人挑战只剩少量 HP 的 Boss：不双重击杀、不超发最终奖励，伤害与经验口径一致
- 同玩家同时狩猎/锻造/挑战，角色与资产版本不会丢失更新
- 排名挑战与阵容修改、榜单变动同时发生，规则和结果可解释
- 重启之后到期拍卖与 Boss 生命周期可恢复，维护任务重复运行无额外副作用

### 端到端与安全

从新账号完整走到队伍、狩猎、升级、换装、锻造、拍卖、排行与 Boss；验证空状态、缺钱、冷却、无权限、重复点击、返回与刷新。检查管理授权、CSRF、XSS、参数篡改、ID 越权、日志泄密和文件路径注入。视觉验收覆盖参考布局与关键战报；不能只看首页。

### 首次完整发布的硬门槛

1. 功能矩阵中全部首发项通过验收；每个排除项均有依据或已批准决策
2. 所有发布内容引用完整，所需效果处理器全部实现；无 TODO 技能、空按钮、静默降级
3. PHP 8.4.26 下完整测试通过；应用与锁定依赖无未处理 warning/deprecation，静态分析基线不靠忽略新增错误维持
4. 资产、拍卖、Boss、排行的并发和故障注入测试通过
5. 无已知可刷资源、越权改档、重复领奖或高风险认证缺陷
6. 部署环境的备份恢复、空库安装、首发初始化和失败回滚实际演练通过
7. 以约定并发数、战斗复杂度和数据量完成性能测试；HTTP 延迟、战斗耗时、事务锁等待、任务滞后有明确通过阈值
8. 构建产物排除旧入口、运行存档、凭据和管理后门；日志不记录密码/令牌
9. 发布后数据库迁移仍须版本管理；“不迁移旧存档”不表示以后可以随意删新版玩家数据

## 10. 实施前只需锁定的少量决策

### 需要产品确认

- 功能追踪清单中真正有争议的规则与开关：例如拍卖是否首发默认可上架；共享 Boss 与有效排行榜保持哪套被确认规则。已明确的功能不重复征询
- 目标部署环境和大致规模：可安装哪些服务、是否单机、预计同时在线/同时战斗量、可接受维护窗口
- 运行时是否必须长期严格锁死 8.4.26，还是以它为验收基线并允许后续安全补丁；当前计划严格尊重已指定版本，不自行升级

### 已选择的工程基线与实施核验

- 框架：优先能够直接提供路由、请求校验、会话/CSRF、模板、数据库迁移、测试和 CLI 的成熟方案；先根据部署条件选择，再锁定正式版本。不在本文未经官方资料核验就宣称某框架版本已兼容目标环境
- 数据库：优先支持可靠事务、约束、行级锁和生产可运维能力的关系型方案。选择前核对官方版本文档、PHP 驱动、部署约束和并发测试需求；不同时兼容多种数据库来增加首版负担
- ORM 或直接 SQL：可按复杂度混用，但模块边界、事务所有权和锁行为必须显式可见；不能让 ORM 自动保存掩盖跨对象结算顺序

建议实施时写一页技术决策记录，把选定版本、官方依据、部署理由、事务语义、替代方案和放弃原因固定下来。用户不必逐个批准类名或接口，只确认会改变玩法、部署成本和首发范围的选择。
